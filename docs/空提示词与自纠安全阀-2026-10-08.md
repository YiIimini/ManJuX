# 「短篇不能正常渲染」—— 自纠安全阀把空提示词的正确修复判成了"改坏了"（2026-10-08）

用户原话：**「短篇咋不能正常渲染视频，排查处理解决」**。

现场是《外卖员写了七千封回信》（短篇，10 集，09:13 起跑批量产线）。下面每一句都有实证据：
平台日志、真机 `plan.json`、以及跑起来的自纠代码路径。

---

## 1. 现象（日志原文）

```
09:27:39 [外卖员写了七千封回信·第01集·最冷血外卖员][assets][success] ✔ 资产就绪:15/15(角色 4 位 / 造型卡 4 张 / 场景 5;库复用 0)
09:27:39 [..][render][error] ⛔ [fatal] shots[7](id=8): h3_prompt 为空 —— 该镜没有可提交的提示词（引擎收到空提示词会出一帧近全黑，实测第 02 集镜 15 达 94%!）(MISSING)；重跑剧本分镜补上这一镜，或在故事板里手改
09:27:39 [..][render][error] ✕ 阶段失败:方案里有 1 处**致命**问题 —— 不启动渲染（否则必然白烧显卡）
09:27:39 [..][pipeline][error] ✕ 管线中止于「渲染出片」
09:27:49 [][novel][error] ✕ 批量产线暂停于 1/10:…运行失败,不自动跳集
```

两件事同时成立：

1. **渲染门是对的**：空提示词渲出来就是一帧近全黑（历史实测 94% 黑），不启动是对的。
2. **但这不是"模型没写"那么简单**：剧本阶段跑过自纠一轮，而 `plan.json` 里第 8 镜
   **结构化字段全在**（动作 / 台词两句 / 机位 / 尾帧状态 / prop_ids / vo_kind），**只有 `h3_prompt` 是空串**：

```
镜数=8，空正文的镜=[8]
  #8 duration=10 场=scene_station_office_door 台词=2 动作="何仕把工牌塞进兜里撂下狠话转身要走；陈声掏出手机点了三下…"
```

也就是说：**平台明明有一条"空提示词要喂回去重写"的自纠规则，它跑了，但修复被自己的安全阀退回了。**

## 2. 根因（一处，可复现）

`internal/director/repair.go`：

* `collectRepairable()` **确实**把空提示词列进自纠名单（2026-09-30 加的，注释里写着"空提示词要修，不能跳过"），
  给模型的指令是"这一镜没有正文，**把整镜写出来**"。
* 但采纳闸门 `adoptRepaired()` 里有一条"台词条数不许变"：

  ```go
  beforeLines := strings.Count(sh.H3Prompt, "<d>")   // 空原文 → 0
  afterLines  := strings.Count(got, "<d>")           // 合格的修复 → 2（计划里那两句）
  if afterLines != beforeLines { return false }      // ← 0 != 2 ⇒ 退回原文（原文就是空的）
  ```

  这条闸门的本意是"台词是内容、不许被自纠增删"——对**有正文**的镜是对的；
  但对**空正文**的镜，合格的修复**必然**要从 0 补到计划里的那几句 ⇒ 于是**正确的修复被判成"改坏了"**，
  `plan.Shots[8].H3Prompt` 永远停在空串 ⇒ 渲染阶段被致命门拦住 ⇒ 整条产线中止
  （而且资产阶段 15 件全生成完才拦，白跑一整段）。

> 顺带说明为什么"短篇"更容易撞上：短篇一本书压成 10 集、每集 8 镜，模型一次要写的正文量大
> （本次自纠一轮里就有 4 镜词数超标被点名重写），漏掉某一镜的正文概率更高；
> **这不是短篇专属缺陷，任何书任何一镜漏正文都会卡在这里。**

## 3. 修法

1. **`adoptRepaired` 的空原文例外**（`internal/director/repair.go`）：原文没有 `<d>` 时，
   允许补到**计划里那几句**（`project.PlanSpokenTexts(sh)`，含旁白），仍不许凭空多出计划外的台词。
   原文有条数时行为**一字不变**（`repair_test.go` 那条老守卫照旧成立）。
2. **剧本阶段点名**（`internal/pipeline/stages_script.go`，存盘之前）：
   `project.EmptyPromptShotIDs(plan)`（新增）列出仍然空的镜，warn 说清后果与改法 ——
   此前用户只能在**资产阶段白跑完之后**才看到渲染门报错；现在资产阶段之前就知道是哪几镜。
   方案照常存盘（可以在故事板里手改那几镜的正文，已生成的资产还能复用）。

## 4. 判据与反向验证

* `internal/director/repair_empty_prompt_test.go`（夹具 = **真机第 8 镜的形态**：空正文 + 两句台词 +
  真动作文本；修复产物是一份**合规的**六段式提示词）：
  * 空正文 + 补上计划里那两句 ⇒ **必须采纳**（这正是卡死的那一步）；
  * 补出**计划外**的第三句 ⇒ 拒；把两句弄没了 ⇒ 拒；
  * 原文**有** `<d>` 时条数仍然不许增删（老行为不许被改坏）；
  * 自纠名单要点名 #8，且"写整镜"的指令里带上时长与动作原文。
* `internal/pipeline/empty_prompt_wiring_test.go`：剧本阶段的点名必须在、必须说清后果、
  必须排在 `SavePlan` **之前**。
* **反向验证 3 处**（全红后逐条回滚、复跑三包绿）：① 空原文仍按 0 条算 ⇒ 正确修复被拒
  ② 自纠跳过空提示词的镜 ⇒ 名单里没有 #8 ③ 剧本阶段不点名 ⇒ 接线门红。

## 5. 还剩什么

* **真机复验要重跑那一集的剧本阶段**：修好的是"自纠能不能修好空镜"与"提前点名"，
  存量那份 `plan.json` 的第 8 镜**仍然是空的**（自纠已经跑过、当时被退回）。
  两条路：① 在故事板里手写第 8 镜的正文；② 重跑「剧本分镜」——现在自纠会把这一镜补上
  （代价是重排分镜，已生成的资产按卡片 id 复用，不受影响）。
* 本次**没有**改渲染门的定级（空提示词仍然 fatal 拦住整条产线）——那是对的：宁可拦住，也不要渲一帧黑。
