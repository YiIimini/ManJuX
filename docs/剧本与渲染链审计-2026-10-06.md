## 三、五处修改的根因与验证

### ① 失败镜的占位片段进不了合成 ⇒ 用户永远拿不到成片（🔴）

* **现象链**：阶梯三次都失败 → 渲染阶段写黑场占位并播报「占位保住了时长与顺序，缺口在成片里看得见」
  → 合成阶段一句「镜头 N 尚未渲染完成:请先运行『渲染出片』」**把整片拒收**；而那一镜本来
  就渲不出来，重渲又失败（重渲失败还会把 `File` 里上一次的路径一起清空）。
* **根因**（`internal/pipeline/stages_render.go:503`、`:510`）：

  ```go
  placeholderPath := filepath.Join(clipsDir, outName)     // outName = "shot_031"，**连扩展名都没有**
  ...
  c.setShotStatus(..., project.ShotFailed, engName, "", inputFP, ...)  // File 传空串
  ```

  而消费方 `internal/pipeline/stages_qc_assemble.go:399` 的判据是
  `!ok || m.File == "" || (m.Status != ShotDone && !isPlaceholderClip(m))` ——
  `m.File == ""` 在前面短路，**占位那条豁免根本没机会生效**。
* **修法**：占位改用独立文件名 `<outName>_placeholder.mp4`（不覆盖上一次可能还躺在盘上的真产物），
  并把它的**相对路径记进清单**；渲染成功后删掉残留占位。判据抽成
  `assembleClipReject(m, ok)` 一个函数（可测），语义不变。
* **反向验证**：把 `File` 改回空串 → `TestFailedShotPlaceholderIsRecordedForAssembly` 红，
  报的就是「合成阶段会在 `m.File == ""` 处短路」。

### ② 缩短重试丢掉四步装配（🔴）

* **根因**：`stages_render.go:459`（旧）—— `prompt = shortPrompt`，而 `shortPrompt` 来自
  `project.ShortenShotPrompt(shot.H3Prompt, …)`，即**裸正文**。渲染主循环此前拼好的四层
  （身份/画风锚定 → **参考图权威清单** → 道具锚定 → 转场字幕）**全部丢掉**，而参考图照旧提交。
  参考图清单的全部意义就是止住 `<Picture>` 编号混乱（2026-09-25 镜头 6 角色漂移的根因，见
  `refmanifest.go` 头注释）。
* **修法**：四步装配收成唯一入口 `assembleShotPrompt(...)`，正常渲染与缩短重出**都走它**；
  顺便把 `inputFP` 重算成**真正渲出去的那份**提示词（原来记的是没渲过的那份）。
* **反向验证**：改回 `prompt = shortRaw` → 测试红，实得 `"detailed_description:\nGUOFENG. [Shot 1] …"`
  对 应为（含 STYLE AUTHORITY / ON-SCREEN TEXT / SCENE TRANSITION 三段的完整装配串）——
  一次失败就把"丢了多少层"打在屏幕上。

### ③ 空提示词闸门被光照锚击穿（🟠）

* `ShotRenderPrompt` 会**就地往 `shot.H3Prompt` 追加**场级光照锚（`prompts.go` 的
  `sceneLightingClause`），而空提示词判据写在它**之后**（`stages_render.go:320`）⇒ 只要这一镜的
  场景卡有 `light_state`，空提示词就变成"一句光照短语"，闸门放行 → 引擎照它出帧（正是 2026-09-30
  那批黑帧的形状）。
* **修法**：装配前留一份 `rawPrompt`，判据看**装配前**那份。
* 这里还顺手把 `project.ShortenNote`（"砍掉的秒数要不要补由你定"）接上了播报 —— 它此前
  **写了但全仓没人调用**（只有测试引用），用户从不知道砍掉的内容需要决策。

### ④ 参考图：三处只判"字段非空"（🟠）

* `refs.go` 里角色定妆照那一支早就是 `project.FileOnDisk(dir, a.File)`（2026-09-28 审计定的判据），
  但**场景卡**（`:160`）、**内心镜的 Q 版顶替**（`:126`）、**系统镜的机器人/面板**（`:175`/`:183`）
  仍只判 `a.File != ""`。资产表里的**悬挂条目**（"鬼条目"，`stages_assets.go:436` 自己写着
  "用户删掉的条目会复活"）照样进参考图列表 ⇒ 引擎 `UploadImage` 打开不存在的文件 ⇒
  **整镜失败**（不是降级出图），再叠加缺陷 ① 就是整片合不出来。
* **修法**：三处统一走 `project.FileOnDisk`；Q 版顶替不了时按老规矩回落本人定妆照，
  但**如实播报**（"内心戏本该由 Q 版演出"这件事不能静默）。
* **守卫判据是结构性的**：`参考图列表里每一张都必须在盘上真的存在`（不是"看代码有没有写 FileOnDisk"）。
  反向验证把四处改回 `!= ""` → 三个用例全红，且逐张点名了那个不存在的路径。

### ⑤ 剧本：缺节只 warn，而告警的动作实际做不到（🟠）

* **两个错叠在一起**（`internal/server/novels_jobs.go`）：

  1. 「已经在像样的剧本」只看**字数** `>= 800`（旧 `:298`）。而拆集那一步的 LLM 被要求写
     **400-700 字的剧情节拍 brief**（`novels_split.go:40-41` 的 `briefMin/Max`）—— 模型常态超发，
     于是一份"事件清单"（没有场次头、没有目的/冲突/爽点）被当成剧本**长驻**，分镜从此少依据；
  2. 告警写着「建议重跑本阶段」，而重跑**正是被 ① 那条字数判据挡住的** ⇒ 用户按建议操作，
     **什么都不会发生**。给一个做不到的动作，比不告警更糟。
* **修法**：
  * 判据换成 `briefIsUsable`（**字数 + 结构**，结构判据是既有的 `missingBriefSections`）；
  * 缺结构的旧稿先**备份**成 `source-brief-prev.txt` 再重写（那可能是作者手写或技能侧给的稿子；
    备份写不进去就**不覆盖**，并说清为什么没做）；
  * 生成后缺节 → **把缺的节名连同上一稿喂回去补写一轮**（本仓对模型的一贯口径，见
    `internal/director/repair.go`），只采纳"缺节真的变少且不是空稿"的结果（`adoptRepairedBrief`）；
  * 收尾告警改成**代码真会做的事**：「**重跑本阶段会重写这一集**（旧稿会备份成 source-brief-prev.txt）」。
* **反向验证**：把 `briefIsUsable` 改回"只看字数" → `TestBriefIsUsableNeedsStructureNotJustLength`
  红，报「800 字以上的节拍 brief 被判成可用 —— 分镜会拿它当剧本用、重点只能自己猜」。

## 八、第三个审计（分镜）补充：**自纠环漏了第三个入口**（已修）+ 三条新记

三路审计里的分镜那一路回来得晚，里面有**一条同型缺陷**，已当场修掉，另有三条记入清单。

### 已修 ⑥ 五步专职会话**从来没跑过自纠环**（🔴）

`RepairPlan`（把"一镜到底""词数超标""空提示词"这类**机器可判定**的违规连同原文回给模型改一次）
全仓只有一处调用：`director.go:319` 的 `finish` 闭包。而那个闭包只覆盖 `Generate` **函数内部**
的两条路（单轮直出 / 分批）—— 第三个入口 `GenerateSessions`（五步专职会话，设置页
`split.five_sessions` 开启后走它，正是用户 2026-09-28 自己定的架构）**是另一个函数**，它当时没被覆盖。

后果（与 2026-09-28 那次"分批路径不跑自纠 ⇒ 35/35 镜全一镜到底"**完全同型**，只是换了个入口）：
开五步会话的机器上 ① 自纠环整条不存在；② `enforceStyleLock` 没跑；③ `normalizePlan` 没跑
（"说话人不在画面里"的台词不会被标成画外音、Q版/系统素材 id 不会补）—— 两条路产出的方案连
**归一化程度**都不一样，而它们是同一条流水线的同一个阶段。

修法：把收尾提成包级 `finishPlan(ctx, client, plan, sourceText, opt)`
（画风锁定 → 归一化 → 自纠一轮），**三个入口都调它**。幂等性由 `RepairPlan` 自己保证
（没有可修项时一次 LLM 调用都不发），所以上游已经修过不会造成重复开销。

守卫：`director/finish_paths_test.go` 从"钉住闭包"升级为三条判据——
① `RepairPlan(` 在 director.go 里恰好一处、sessions.go 里 0 处；
② 三个入口都 `return finishPlan(...)`；
③ **行为断言**：`finishPlan` 在 `client=nil` 时仍必须完成确定性的两步（夹具用真实形态：
源文本带 `全局风格:GUOFENG`、一条"谢无咎说话但他不在本镜画面里"的台词）。
反向验证：把五步会话改回 `return plan, nil` → 第②条立刻红，报的就是"漏了它，开五步会话的机器上
自纠环整条不存在（与 2026-09-28 那次同型）"。

## 九、三条口径题：按**最优方案**落地（本轮，用户拍板"你自己定最优"）

§五-1（道具进不进参考图）、§五-2（系统镜"场景图是不是最后一张"）、§八-12（`<d>` 部分缺的级别）
都属于"要拍板"的一类。按"**质量收益最大 + 契约/存量代价最小**"逐条定下来，并全部落地。

### ① 道具**不进** H3 参考图集合 —— 但把"对号"补全（原来只做了一半）

* **决定依据**：参考图槽位上限 9 张，超了由 `capRefsToLimit` **从尾部裁** —— 而尾部正是场景图；
  再把道具图塞进去，"裁掉谁"就变得不可预测。而且道具出图是 1:1 白底单件的商品图纪律
  （`PropImagePrompt`），当参考图有"把白底物件糊进画面"的风险。用户 2026-09-27 的定调
  （`refs.go:166-171`）本来就是这个方向 ⇒ **维持不动**。
* **但真正的漏子是"对号只做了一半"**：器物锚定的唯一机制挂在 `prop_ids` 上
  （`EnsurePropAnchors`），而 `RemapPropRefs` 对**空引用**是直接 skip ⇒ 正文里写着"碑刀握在右手"，
  锚定却一次都不发生（实测那一集 25 镜提到刀/烙铁/名册，`prop_ids` 全空）。
* **落地**：新增 `FillMissingPropRefs`（在**唯一自愈入口** `HealPlan` 里调用），按**卡片名 / id 强键**
  从正文 + 动作 + 尾帧状态里补 `prop_ids`；长键优先（"名册板"命中后不再补"名册"）；
  **不用**描述里的散词（宁可少锚，也不锚错）；补了几处**如实播报**（director 的自愈播报 + `cmd/preflight`）。
* 顺手纠一处**口径误引**：平台代码注释把"道具不给图"写成官方规则，而官方 `ref-en.txt` 明写
  `<Subject N>` 含 props/objects —— 这是**平台自设约束**（理由如上），注释已改成如实说法。
* **守卫**：`internal/project/heal_props_dialogue_test.go` —— 补缺 / 已有引用不许被碰 / 没提到的不许塞 /
  动作命中要补 / 英文散词不算点名 / 长名优先 / 幂等。
  **反向验证**：把那一步改回"空引用跳过" → 门红（报"镜 1 该补上 prop_blade，实际 []"）。

### ② 系统镜的清单按**实际位次**说"场景图是第几张"

* `RefManifest` 对场景那一行硬写 `it is the LAST picture`，而系统镜的机器人 + 全息面板两张图
  **排在场景图之后** ⇒ 清单自己就错了一句（而它开篇宣称 `OVERRIDES any picture count or picture
  number stated anywhere above`）。模型对"还剩几张"最敏感，这一句说错等于把权威性抵消掉。
* **落地**：末尾那条文案**逐字不动**（提示词进渲染指纹，改一个字＝存量项目全部参考图镜重渲），
  只在**非末尾**时改说 `it is NOT the last picture (N picture(s) follow it)`。
* **代价如实记**：只有**系统镜**的提示词变了（这些镜的指纹会失配 ⇒ 重渲一次）；普通镜逐字不变。
* **守卫** `TestRefManifestSceneSaysItsRealPosition`：先复核"系统镜的场景图之后确实还有图"
  （夹具不真就 Fatal，防止测了个空），再断言非末尾不许出现 LAST、末尾那句逐字保持。

### ③ `<d>` 部分缺：**确定性补齐**，而不是再加一道会永远沉默的契约门

* 两条路各自的代价：加契约门（warn）→ 本仓对"只有一行 warn"有成见，模型/用户都容易忽略；
  加 fail → 会拒收技能侧老包（误拦比漏拦更糟）；确定性追加 → 那句话在片段里会晚出现一点。
* **选定确定性补齐**：`FillMissingDialogueTags` 改成**逐句对账** —— 先抽出正文里已有的 `<d>…</d>`
  （**去标点 + 小写**后比较：官方要求标点归一成 `, . ? !`，逐字符比较会把"同一句"判成没说 ⇒ 重复配音），
  只把**确实没说过**的那几句追加到末尾，逐字用计划里的原文。
* **边界**：正文整体为空就**不补**（往空正文里塞台词会造出"只有台词、没有画面描述"的镜，
  那是空提示词闸门 + 自纠环的事）；那种情况仍由既有的 G029（fatal）兜着。
* **为什么不再加契约门**：补完之后"每句计划台词都在某个 `<d>` 里"就成了一条**幂等不变量**，
  一道在自愈之后**不可能触发**的门等于没写（本仓原话：门写了不接线＝没写）。
  判据落在守卫测试的不变量断言上。
* **守卫**：同上测试文件 —— 部分缺只补缺的那句 / 标点不同不算缺 / 幂等 / 空正文不补 / 旁白也算一句 /
  `HealPlan` 真的接上了这两件。**反向验证**：把判据改回"只要有 `<d>` 就整镜不补" → 门红。

### ⑪ `cuts` 活过来了：在**唯一读取边界**从正文回填小镜头结构

* 事实复核（比 §八 记的更准）：`CutCoverageIssues`（4 秒以上必须切 / 刀数上限）**早就在读正文**
  （`cuts.go:222` 自己调 `ParseCutsFromPrompt`），所以那两条一直是活的；真正空转的是 `CutIssues`
  —— **每刀 1.5–4 秒 / 首刀为 0 / 时间点严格递增 / 各刀之和 = 片段时长**（用户文件里的硬要求），
  它只看结构字段 `shot.cuts`，而那个字段**从来没被写过**。
* **落地**：`HealPlan`（唯一自愈入口，`LoadPlan`/预检/渲染三个消费方共用）里调
  `plan.FillCutsFromPrompt()`，把正文里的 `[Shot N] At MM:SS.mmm` 回填成结构；
  补了几段**如实播报**（渲染日志 + `cmd/preflight`）。
* 为什么回填是安全的：解析器**只认规范的多镜形式**（首刀为 0、时间点严格递增），读不出来就返回
  nil（"没有结构数据"，不编）；回填**幂等**（已有结构不覆盖，人工改过的不会被冲掉）；
  `CutIssues` 是 **warn** 级（`plan_checks.go:552`），不会因为回填出问题而拒收任何包。
* **守卫**：`TestCutsAreBackfilledAtTheReadBoundary`（合规的 4 刀 × 2.5 秒 = 10 秒：回填 4 刀且
  判据不误报 + 幂等）、`TestBackfilledCutsMakeCutIssuesLive`（第 5 刀越过片段时长 → `CutIssues`
  必须报"有刀落在片段时长之外"）。反向验证：注掉回填那一行 → 两条门立刻红。
* **附带教训（夹具）**：第一版夹具把四刀挤在同一行、并把 `[Shot 1]` 跟在风格句后面 ——
  解析器正则锚行首，于是读回 0 刀。**门当场就响了**，夹具按真实形态改成"一行一刀"。

### ⑬ 结构字段真的进渲染输入了：装配点按「缺什么补什么」补一节

* 事实复核：`view` / `view_note` 其实**由模型按契约写进正文**、并有一道门对账
  （`plan_view_contract_test.go`）；`camera` 被 QC 简报消费（`stages_qc_assemble.go:107`）；
  **真正零消费的是 `end_state` / `positions` / `offscreen`**（只有必填与对号门），
  而 `view` / `camera` 的问题在另一头：**模型漏写时只多一条 warn，画面照旧**。
* **落地**：新增 `internal/pipeline/shot_spec.go` 的 `EnsureShotSpecClause`，挂在**唯一装配入口**
  `assembleShotPrompt` 的最后一环（第⑤步），逐行"缺什么补什么"：
  机位词 / 运镜 / **尾帧状态（continuity handoff）** / 每个出场角色的**画面位置** / **离屏角色**。
  正文里已经有那个串就不再写（提示词词数预算紧，官方 350-500 词）；一行都补不出来就原样返回；
  marker 保证幂等；键排序保证**输出稳定**（否则同样的计划两次拼出的串不同，指纹会无谓失配）。
* **传导就是解药**：这些字段写进提示词之后，"用户在工作台改 `end_state`"⇒ 提示词变 ⇒ 指纹失配
  ⇒ 会重渲。守卫 `TestShotSpecChangesReachTheRenderedPrompt` 直接断言这件事（改 end_state /
  offscreen ⇒ 装配结果必须变，且重建后逐字一致）。

  "`<d>` 外不许出现可避免汉字"那条卫生门 —— 这一条写在 `shot_table.go` 的口径里，此处只做声明。
* 反向验证：把 `EnsureShotSpecClause` 从装配链摘掉 → `TestShotSpecChangesReachTheRenderedPrompt`
