# 装配层换成熟引擎（MoviePy）——「替代方案，是全部」第一环

> 用户 2026-10-09 原话：「替代方案，是全部，你TM根本就改不好，别继续不停的补丁了」。
> 所以这一轮**不打补丁**：把平台自己拼的装配链整条删掉，换成成熟引擎，并把它接进「合片」入口。

## 一、为什么非换不可（真机取证，不是推测）

平台此前用**自己拼的一条 ffmpeg `-filter_complex` xfade 链**把 N 个镜头串起来。

真机《被开除一年后，我回公司送水·第01集》的成片（已删除前取证）：

| 项 | 实测值 |
|---|---|
| 画面轨 | **23.708333 秒 / 569 帧** |
| 音轨 | **122.498917 秒** |
| 569 帧 = 前 3 镜（192+175+204）− 2 帧同场硬切 | ⇒ 第 4 镜起**一帧画面都没有** |
| 日志 | 「✔ 成片就绪 122 秒」 |

**根因**：xfade 的 `offset` 用「按秒连续累加」的量，而 xfade 每步输出落到**整数帧**上
（标称 15.258s → 实测 366 帧）；过渡窗口末端一旦越过前一镜的真实末帧，ffmpeg 的 xfade
就**静默丢弃后面所有输入，而退出码仍是 0**。在一个 15 镜的成片里这点误差必然攒出来。

「自己算偏移、自己拼图」正是成熟引擎每天在做的事。这一环交给它。

## 二、换成了什么（谁干什么）

| 原来（平台自写） | 现在（成熟件） | 依据 |
|---|---|---|
| 拼接 + 接缝转场：自写 xfade 滤镜链 | **MoviePy 2.2.1**（Zulko/moviepy，★14,964 / MIT / 2026-08-26 活跃）`concatenate_videoclips(padding=-重叠)` + `CrossFadeIn/Out`（**画面与音轨都交叉淡化**） | 真机 6 镜跑通 |
| 硬切（零重叠）：自写 `-c:v copy` + concat 音频滤镜链 | **ffmpeg concat 解复用器 + `-c:v copy -c:a flac`**（零重编码、无任何时间算术） | 真机；且复制出来的时间轴不对时会**自动退回 MoviePy** |
| 时间轴：平台按 fades 累加推 `starts` | **引擎回报** `timeline.json`（每镜真实 start/duration） | 一处算、处处一致（字幕/音轨/BGM 全读这一份） |
| 接缝音频：`audio.SolveCut` 按静音落刀 + **砍掉**重叠段 | 引擎在接缝处**交叉淡入淡出**（不切内容） | 「配音不完整」的根因本来就是"砍" |
| 拼完校验：`verifyStitchedLength` | 引擎内自检：画面比标称短 0.5 秒 ⇒ `ASM-FAIL` 拒交付；平台再校一遍 timeline | 宁可失败，也不交付半部片子 |

**删掉的自写代码**（不是留着不用，是删掉）：`internal/compose/xfade.go` 整个文件、
`stitchWithTransitions`、`stitchCut`、`seamAudioWindows`、`seamFeedback`、`xfadeOffsets`、
`verifyStitchedLength`，以及「平台按 fades 累加推起点」这条口径。

## 三、真机实测（同一台机器、同一批镜头、同一套参数）

| 场景 | 输入 | 引擎输出 | 耗时 | 产物 |
|---|---|---|---|---|
| 3 镜硬切 | Σ视频轨 29.875s | **29.874 秒 / 717 帧** | 63.0s | `cut.mkv` |
| 2 镜 0.5s 叠化 | Σ19.250 − 0.5 | **18.749 秒 / 450 帧** | 26.5s | `fade.mkv` |
| **6 镜混合**（4 处 1 帧同场硬切 + 1 处 0.5s 换场叠化） | Σ58.208 − 0.667 | **57.499 秒 / 1380 帧** | 313.5s | `ep6.mkv` 13,700,387 B |

硬切那一路的过程值得记下来：concat 复制出来的是 **30.046 秒**（比各镜合计多 0.171 秒
= 每处接缝多 2 帧**空隙**，播放器会停住那两帧）。引擎**实测发现后自动退回 MoviePy 重编**，
拿到 29.874 秒 / 717 帧 —— 正确值。

### 过程中被真机咬出的、我自己的两个缺陷（都已修）

1. **mkv 的 `stream.duration` 是 N/A** ⇒ 自检把「30 秒的画面」读成 **0 秒**、音轨报 `0.000`
   —— 自检形同虚设。修法：兜底顺序 流时长 → 帧数/帧率 → **最后一张视频包的 pts+dur**（只读索引不解码）。
2. **MoviePy 把 `shot_001` 读成 9.900 秒，而视频轨只有 9.833 秒（236 帧）** ⇒ 若不处理，
   每一镜末尾会多出 **2 帧重复画面**（正是用户最反感的「定格」形态）。修法：按视频轨实际时长裁齐
   —— 真机 6 镜里 **5 镜命中**，每一镜都如实播报裁了几帧。
3. **色彩标记在编码那一步根本写不进去**（换引擎后新暴露的一条）。引擎（MoviePy 走 rawvideo 管道）
   会把逐镜写在片段上的标记**全部丢掉**；而"补写标记"这件事，实测**系统 ffmpeg 9.0.1 与引擎自带的
   7.1 都不认** `-colorspace / -color_primaries / -color_trc / -color_range` —— 编码器把**输入帧自带**
   的色彩属性写出去（H3 源片是 `bt709 / iec61966-2-1 / tv`），连 `-x264-params colorprim=…:transfer=…`
   也照样被盖。**只有 `-c copy` 的重新封装认这四个选项**。
   修法：色标**只在复制流那一步写**（`apply_color_args`，一处收口），写完再探测一遍并把四个值
   原样打进日志。真机复验：`color_space=bt709 color_primaries=bt709 color_transfer=bt709 color_range=tv`
   —— 与"不给标记"的对照产物（`unknown/unknown/unknown/tv`）逐项可比。
4. **引擎环境落点算错了**（第一版 `filepath.Join(c.store.Root(), "tools")`，而 `store.Root()` 是
   `<数据根>/projects`）⇒ 真机第一次合片会去一个**空目录**重新联网引导一遍。现在落在
   `<数据根>/tools`，并**加了门**（`TestEngineToolDirIsDataRootTools`：改回 `store.Root()` 就红）。

## 四、平台侧怎么接（Go 侧）

- `internal/compose/engine.go`：`go:embed assemble_mpy.py`（脚本随二进制走，不依赖工作目录）+
  manifest 生成 + stdout 三态解析（`ASM ` 进度 / `ASM-FAIL` / `ASM-DONE`）+ timeline 校验。
- 引擎的每一句 `ASM ...` 原样进「合片」日志 —— 用户能看到引擎裁了几帧、走了复制还是重编。
- **python 运行环境**：`<数据根>/tools/mpy-venv`（本机已建：uv 0.12.23 + moviepy 2.2.1 + Python 3.14.6）。
  找不到时用 `uv` 自动引导（没有 uv 退回 `python -m venv` + pip）；引导失败**如实报错并给出手工命令**，
  绝不静默退回旧链（旧链已删）。
- `Params.ToolDir` 由 pipeline 传 `c.store.Root()/tools`；`MANJUX_MPY_PYTHON` 可覆盖解释器。

## 五、边界与代价（如实）

- **速率**：6 镜 58 秒成片耗时 313.5s ≈ 5.4× 实时（CPU x264 veryfast）。**没用 nvenc**
  —— 换编码器要按硬件/画质拍板，没做。
- 中间轨是 **flac/mkv**（58 秒 ≈ 13.7MB）：无损纪律不变，后面响度归一/终混还要各编一次。
- **同场接缝保留 1 帧**（1/24 秒）是刻意的：视觉上等同硬切，但引擎的几何一个字都不用改。
- 存量项目**不用重渲**，重跑一次「合片」即生效。
- 「全部换」的剩余环（按用户要求继续，逐环都在真机素材上给实测数字）：
  人脸一致性 → 本机已装的 `ComfyUI-H3-FaceRefine`；字幕对齐 → `stable-ts`；
  质检 → `PySceneDetect` / `qctools`。**LLM 编排（剧本/分镜/资产卡）没有成熟替代品**
  —— 那一层是本平台的产品能力本身，会如实标注，不假装有现成件可换。
