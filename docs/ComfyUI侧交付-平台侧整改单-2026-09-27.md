## 1. 必改（P0）

### P0-1 历史基准口径更正：带参考图的真实成本是 310 s，不是 181–213 s

**现象/依据**：`docs/红果对标-画质配置方案.md`、`COMPATIBILITY.md` §八 等处在引用 Singularity 换装实测（2026-09-24）的 **181–213 s / 79.9%**。
那批数字是在**参考图被静默丢弃**的情况下测的（当时提交键写成聚合数组 `ref_images=[...]`，ComfyUI 只认点号键，聚合数组被丢成空 dict 且不报错）。
2026-09-27 用点号键重测（同 seed / 同参数 / **3 张参考图** / 同 `--reserve-vram 4`）：**整数张参考图进来后是 310.1 s / 峰值 22,186 MiB(90.7%)**。
帧指纹互证参考图确实生效：同 seed 同参数下 09-24 首帧 `87e4fed8…` vs 今日 `dbeb79fb…`，逐帧全不同。

**要做什么**：
1. 把平台侧文档里引用的**绝对**耗时/显存，统一改注明"口径"，或换成 2026-09-27 那一组；
2. **凡是按"单镜 ≈200 s"推出来的产能/排期，按 ×1.55 重算**（310.1 / 200）；
3. 相对结论（int8 与 w4a8 的差距、Singularity 与原版的差距）**不受影响**，不必推翻。

**验收**：平台文档里不再出现无口径的 181–213 s；产能估算给出口径标注。

### P0-2 quality 档的静默回退要可见

**现象/依据**：`internal/engine/comfyengine/engine.go:844` 是量化门：
`if !isQuantizedBase(unetFor(job, c)) && modelFileExists(...)` → 量化底模直接走不进 Acc-8Step 分支。
本机 **4 个 H3 底模全部是 int8/w4a8** → 用户选 `quality` 时**必然**回退 Turbo，而**回退是静默的**。
这套回退本身是**有意设计且有测试的**（`accel_lora_test.go:80 TestAccelQualityLoraGuard`、`:152 TestAccelQualityLoraGuardNoAccFile`）——所以我说的**不是改逻辑，而是让结果可见**。

**要做什么**：在选定档位与最终 LoRA 不一致时，产出一行**可检索的提示**（启动日志 + 渲染报告的档位行，例如"quality 档因量化底模回退为 turbo"）。CLI/设置页有档位显示的地方同步。
**代价**：极小，不动选路逻辑、不动既有测试。
**验收**：在本机选 `quality` 跑一镜，日志/报告里能看到回退说明。

## 2. 需你拍板（P1）

### P1-1 步数与 LoRA 锚定：现在是"4 步蒸馏 LoRA 跑 8 步"

**依据**：档位选路 `accelLoraFor`（`accel_refine_test.go:32/46/93/98/124` 覆盖了 turbo/express/refine 三档的期望值）在 turbo 档挂 `TurboLoRARef2VA` = `minimax_h3_ref2v_turbo_4step_v0.1`（**4 步锚定**），而实际步数由 `accelSteps()` 决定（`accel_refine_test.go:11` 要求"档位→步数只有一份实现"）——默认 8。

**三个选项（都实测/核过）**：

| 选项 | 动作 | 实测代价 | 副作用 |
|---|---|---|---|
| A. 换 8 步锚定 LoRA | 把 turbo 档的 ref2v/fl2v LoRA 换成 **`minimax_h3_ref2v_turbo_8step_v1.0_768p_comfyui_bf16`** / **`minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16`**（**今天已补齐在盘**） | 同 8 步下 **310.1 → 325.2 s（+4.9%）**，峰值反而低 511 MiB | 需改档位映射；画质差异**单次样本看不出**（见下） |
| B. 步数改 4 | turbo 档步数 8→4 | 库里对 5090/int8 的实测为 4 步 **2.65×** | ⚠️ 该实测同页记录"**4 步音频有杂音/削波，8 步最安全**"——要用必须先验音频 |
| C. 不动 | — | — | 维持现状；"错配"只是理论问题（本轮单次对照未见可见损失） |

**必须说清的一点**：我做了 A 的对照（同底模/同 8 步/同 3 张参考图，4 帧横排目视：A 旧挂 vs I 新挂，图在 `_maintenance\taomate-compare\`），**两者是同一场景、同一人物、同一动作节拍，均无肉眼崩坏** → **不要把这轮读成"换 8 步版画质更好"**。8 步版目前的价值只在**锚定对齐**上；要定论得在交付规格下做多镜 A/B + 明确评分口径。

### P1-2 抽卡/筛方向档（TaoMate 3 步）是否上

**依据（实测）**：同机同图同 seed，`Singularity int8 + TaoMate + 3 步` = **156.4 s** vs 现行 `310.1 s`（**1.98×**），**音轨完好**（aac 双声道），768×1344/124 帧，无肉眼崩坏。
**代价**：需改 `accel` 枚举 + 设置页文案 + `accelLoraFor` 选路（`engine.go` 一带）。
⚠️ **上线前建议先做一次"提示词遵循"抽检**（照你们 `mjxverdict` 那套 young/old 对照的做法）：本轮单图 A/B 显示 **3 步下参考图会压过提示词**（同提示词同参考图，8 步落在暗色厅堂、3 步跟着街景参考图走成了明亮街市）。本项目提示词工程量很大，值得先量化再定它的档位。
**建议定位**：**抽卡/筛方向档**（3 步 + 低分辨率批量筛 → 方向对了再升规格重跑），**不要直接顶掉交付默认档**。

### P1-3 是否引入非剪枝 H3 底座

**依据**：这是**一个开关解锁三样东西**——
- quality 档真正生效（Acc-8Step，现被 `isQuantizedBase()` 挡）；
- `turbo_v4_step600_ema` 这个 T8 包引用 100 次的最新 EMA turbo（**其元数据自声明 `incompatible_base: MiniMax-H3 pruned_*`**）；
- 与 VDN 曲线门禁无关但同属"非剪枝件生态"。

**代价**：非剪枝底模是 **40 GB 级**单件（fp16/fp8），且 24 GB 显存下必须靠 DynamicVRAM 才跑得动。
**我的建议**：**暂不引入**。理由：本机现有剪枝 int8 已经能跑通全部交付链路，解锁的是"画质档"与"一个未验证的社区 LoRA"；收益不确定而成本确定。要引入请先给我一个明确目标（例如"人物特写质量必须提升到 X"），我按目标做对照。

## 3. 建议（P2）

### P2-1 w4a8 回退的定位要改口径
**依据（实测）**：w4a8 权重 10.96 GB vs int8 19.53 GB（差 8.5 GB），但**峰值只低 678 MiB**（21,508 vs 22,186）——因为峰值被 `--vram-headroom` / `--reserve-vram` 压在 24 GB 天花板附近。
→ **显存吃紧时先调 `reserve_vram_gb` 与规格，最后才换 w4a8**；w4a8 的价值是"省盘 + 略快（273.8 s）"，不是"省显存"。
**已就绪**：一键切换 `D:\Ai\ComfyUI\_maintenance\switch-unet.ps1`（`-Show` / `-List` / `-Model <名>`；只改一行、强制 UTF-8 无 BOM、改前验文件在 ComfyUI 视野内、写前备份），**往返切换字节级无损（前后 sha256 一致）**。
⚠️ 注意：**w4a8 与 int8 的 `adaln_t_table` 曲线不同**（w4a8 = `c02a6c11…`，int8 = `ac8727cd…`），换底模会影响 VDN 那条门禁的通过性——曲线是**逐文件属性，不能按家族推断**。

### P2-2 平台文档里的 LoRA 清单同步
`docs/红果对标-画质配置方案.md` 里那份 loras 清单已与盘上不一致（缺 3 个 8 步族、多了挂不上的）。→ 指向 `ComfyUI侧交付-H3-LoRA清单-2026-09-27.md`（含逐个读文件头核出的 patches/rank/锚定/兼容性）。
