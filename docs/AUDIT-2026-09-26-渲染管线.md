### H1 单镜 seed 覆盖不进渲染指纹 → 「换 seed 重渲本镜」静默不生效（原 #19；渲染调度与缓存）

**位置**：`internal/pipeline/stages_render.go:221`

**证据**：

- 单镜种子的唯一收口点在 `stages_render.go:208-209`：`// 镜头种子:唯一收口点 ShotSeed(override > 项目固定种子 > 按角色组合派生)` / `seed := ShotSeed(rp.Seed, seedOverride, shot.ID, shot.Characters)`。
- 但指纹用的是项目 base seed，不是这个 seed：`221: inputFP := renderFingerprint(prompt, refs, rp, mode, rp.Seed)`。
- 跳过分支：`227: if m, ok := manifest[strconv.Itoa(shot.ID)]; ok && shotArtifactValid(m, inputFP, wantFrames, wantModel) {` → `234: "镜头 %d 产物有效,跳过(断点续跑)"`。
- `seedOverride` 由 run 接口透传：`internal/server/handlers_project.go:644` `Seed int64 \`json:"seed"\` // 单镜微调种子(>0 生效:seed+N*101)`；前端 `frontend/src/components/ShotTuneDialog.vue:53` `await api.run(pj.value.project.id, 'render', [shot.value.id], form.engine || undefined, form.seed || undefined)`，并把结果报成 54 行「镜头 ${id} 已按微调参数重渲」。

**对成片/用户的可见影响**：ShotTuneDialog 的 seed 输入框与「随机 seed」按钮（该弹窗的全部意义就是「画布微调 + seed 直渲」）在不改提示词/时长/模式时完全不生效：后端按指纹命中走跳过分支，视频还是旧的那条，前端却弹「已按微调参数重渲」——典型的「能调、看着生效、实际没做」。同一机制也吃掉了「换 seed 不重编码」这条被写进 UI 说明的既定用法（`ComfyView.vue:352`、`ParamsDrawer.vue:201` 都把它当卖点）。

**修法**：指纹必须覆盖真正参与采样的 seed。把第 221 行改成传 effective seed（即 209 行的 `seed`），或给 `renderFingerprint` 增加 runSeed 参数并拼进指纹串。`ShotSeed` 在随机模式（`rp.Seed==0` 且无 override）下由 `nameSeed` 派生、本身稳定，不会引入「每次续跑都失配」；真正随机的 `RandomSeed` 只用在显式抽卡路径，不在这条链上。

### H2 条件缓存键（condCacheName）不含音频参考 / 模式 / 加速档 / CLIP-VAE（4 个模块独立发现）（原 #1 / #23 / #33 / #41；另原 #9）

**位置**：`internal/engine/comfyengine/engine.go:452`（调用点 311-317；引擎进程与显存侧锚点 `engine.go:313`）

**证据**：

- 键的组成：`engine.go:452-455` `func condCacheName(projectID string, shotID int, prompt string, refFPs []string, w, h, length int) string { sum := md5.Sum([]byte(fmt.Sprint(projectID, shotID, prompt, refFPs, w, h, length))) }`；`311-317` 只收集参考图指纹 `refFPs = append(refFPs, ref.Path+":"+fileFingerprint(ref.Path))`——**没有 `job.Audios`，也没有 Mode、Accel、CLIP/VAE 文件名**。
- 而音频是条件的一部分：`303-310` 上传音频 → `519-525` `if len(audios) > 0 { ... inputs["ref_audios"] = auds }` 挂在 `classRef2V` 上 → `324` 把这张含音频的条件图交给 `MiniMaxH3CondSave` 落盘。插件侧确认 `.pt` 存的就是这份含音频的 CONDITIONING（`custom_nodes/ComfyUI-H3-ConditioningCache/__init__.py:47-59、74-91`）。
- 命中缓存时 `318-320` `if e.condExists(...) { condRef = "cache:" + cacheName }`，随后 `663-672` `if condRef != "" { g["24"] = nd(classCondLoad, ...) } else { condNode, latentNode = addConditionNode(...) }` —— **走缓存分支时根本不建 LoadAudio 节点，uploadedAudios 一次都没被用上**。
- 提示词也不区分音频：`internal/pipeline/audio_ref.go:32-48` 与 `55-60` 的标记是固定文本 `<Audio 1>`（不含文件名/内容）；`internal/server/handlers_enhance.go:343-350` 两条音频驱动路径的 Job 都同构（`Mode: "ref2va"`, `Audios: []string{in.AudioPath}`），length 同为 `AlignLength(0)=5`，于是同镜两次音频驱动 = 完全相同的键。
- 同类漏项（另一个模块另行报出，原 #9，位置 `engine.go:563`）：`559-567` `videoVAE := c.VideoVAE; if accel == "express" { const int8VAE = "minimax_h3_video_vae_int8_convrot.safetensors"; ... videoVAE = int8VAE }`，`loaders(c, job.Accel)` 同时服务条件编码图（`550`）与采样图（`659`），而条件节点把它接成 `"vae": link("2", 0)`（`497`）——换档后条件里仍是旧 VAE 编出来的隐空间；模式（ref2va 与 i2v 用的节点不同）与 CLIP/VAE 文件名同样不在键里。

**对成片/用户的可见影响**：同一镜头第二次用**改过的配音**重渲时，缓存命中 → 用第一次那条音频编码出来的条件采样 → 产出的 mp4 里口型与音轨仍是**旧配音**；接口返回 200、日志写「✔ 音频驱动完成」、结果作为独立文件留给用户采纳。整条「精确台词路线」在第二次迭代上静默失效，用户从界面与日志都看不出来，只会以为「模型又没对上口型」。同理，先用 express 档抽卡再用 refine 正式渲同一镜，会表现成「重渲了，但条件还是极速档那份」；在设置页换了 CLIP/VAE 后，由旧编码器算出的隐空间仍被复用。这是「缓存键漏项 → 改了配置却跳过」的典型。

**修法**：把 `job.Audios` 的**内容指纹**（文件 md5/mtime，直接复用 `fileFingerprint`）并进 `condCacheName` 的哈希串，并把 `job.Mode`、`job.Accel`（或实际使用的 VAE/CLIP 文件名）一并纳入——凡参与构建 encode 图的输入都不应缺席；最省事的补充是 `job.Audios` 非空时直接跳过条件缓存（`if c.CondCache && len(job.Audios)==0 && ...`）。加契约测试：同一 shot、同一 refs、同一 prompt、不同音频 ⇒ 缓存名必须不同。注意键一变，旧 `.ok/.pt` 既不会被命中也不会被清（只在删项目时清），建议换键时按项目目录清一次遗留 `.pt`。

### H3 Job.Length 漏传 = 0 被 AlignLength 兜成 5 帧：音频驱动产出 0.21 秒片子还报成功（2 个模块独立发现）（原 #32 / #5）

**证据**：

- 对照：主渲染 `stages_render.go:252` `Length: wantFrames`；局部重绘虽然 Job 里也没写 Length，但**单独把长度传了进去**（`handlers_enhance.go:176` `ctx.shot.Duration*24`，`maskgraph.go:53/174` 用它建图）；契约测试 `graph_contract_test.go:203-227` 明确「条件节点的 length 应原样透传」，说明 length 是平台必须给的上游契约。
- 这条 5 既进了条件编码图（`engine.go:324`），也进了采样图（`engine.go:336` `EmptyLatAV` / Ref2V 的 length），条件缓存键也因此固定落在 `length=5`。

**对成片/用户的可见影响**：音频驱动接口（`server.go:272` 已注册、`frontend/src/store.js:204` 已接线）把 5 帧（≈0.21 秒）当作生成长度：H3 要么直接拒绝这个长度报节点错，要么产出一支 5 帧 / 0.21 秒的 mp4，而 handler 照样 `writeJSON ok:true` 并打印「✔ 音频驱动完成」（`handlers_enhance.go:356-362`）。若节点确实按 `ref_audios` 自行推导长度，则镜头声明的时长在这条路径上完全不受约束，成片时间轴与大纲/其它镜头对不上；同时它的缓存键与主渲染的 `Duration*24` 不同键，进一步让缓存碎片化。Job.Length 的注释只说「17k+5 网格，engine 自行对齐」，把 0 当未填处理，任何漏传 Length 的调用方都会静默得到 5 帧。

**修法**：在 Render 入口对 `job.Length<=0` 直接返回错误（或按 ShotID 从项目侧兜底），不再静默 `AlignLength(0)`；`handleShotAudioDrive` 显式传 `Length: ctx.shot.Duration * 24`（与 mask-fix 用同一个表达式）。补契约测试：音频驱动图里的 length 必须等于镜头帧数。

- 判据：`compose.go:190-211` `args := []string{"-y", "-i", master, "-af", chain}` 之后两个分支都追加 `-c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p`，而此处对视频没有任何滤镜（唯一的 `-vf` 在烧字幕分支里）；上游 master 已经是同规格 x264：硬切路 `-c:v copy`（`:344`）来自逐镜 crf18 的 part（`:113`），叠化路是 xfade 后 crf18 重编的 `master.mkv`（`:460`）。容器 mkv→mp4 允许视频流复制，只有音频加了 `-af`。
- 影响：整集 768×1344 视频被完整「解码→medium 编码」一遍：硬切路径是第 2 代、叠化路径是第 3 代 x264 代次损失，同时白付一次整集 medium 编码时间（分钟级）。与该文件自己的音频纪律（「中间轨一律无损…每过一道就多一层嘶声」）自相矛盾。

### M36 字幕时间窗按「镜头时长÷条数」平均铺开，与真实人声落点无关；且烧录的 ASS 与外发 SRT 是两套时间轴（原 #65）

### M37 人声包络解码失败时静默退回中点切（正是用户报过的「配音不完整」旧行为），且回显统计看不出有接缝没评估（原 #66）

### M38 全链路没有一处写/校验色彩元数据（画质后处理空缺），偏色在管线内不可发现（原 #67）

- `internal/compose/compose.go:106`
