## 按官方 H3 技能重新对齐提示词 + 三视图细节板（2026-09-27）

**根因**（用户指示"平台端的 LLM 分析解析脚本要按仓库 H3 官方提示词技能来，官方已更新"）：
平台内嵌的 H3 规则是从技能侧的**中文转述**里长出来的，与官方一手原文有系统性偏差。逐条核对
`skills/h3-prompt-writing/references/base-en.txt`（T2VA/I2VA/FL2VA/L2VA）与 `ref-en.txt`
（Ref2VA 六段式）后发现：

- **相机词表被压缩**：官方是 12 类动作 ×（方向对）＋ 幅度 ＋ 速度三维，且要求"写成镜头内的
  自然英语动作、**不要**堆在句尾当标签"，并明确"中等幅度/常速通常省略"；平台只列了 12 个词根。
- **切镜措辞与判据缺失**：官方给了 5 种切镜写法，并规定"一次切镜必须带来新信息（主体/空间/
  状态/视角/时间），只改距离或轻微角度时**优先用运镜**"。
- **`summary` 的任务类型前缀写死**：官方是六种（keyframe completion / reference generation /
  video editing / video continuation / audio reuse / audio reference）＋ ` + ` 组合规则，
  且"有音视频文件不等于就有对应类型"。
- **`retention_analysis` 的条目格式与音频标记表缺失**：官方格式是
  `<Subject 1> (appears in [Shot 1], [Shot 3]): fully_preserved - …`，音频另有一套标记
  （fully_copy / partially_copy / reference / weak_reference），并要求"新增的动作/背景/剧情
  **不算**参考保真度损失"。
- **T2VA 的风格句位置写反了**：官方 §5.2 对照表写明 —— Ref2VA 的风格句写在 `[Shot 1]`
  **之前**，T2VA 写在 `[Shot 1]` **之内**；平台两条都写成"之前"。
- **参考音频缺一条关键纪律**：官方 §5.4"只参考音色/节奏/情绪时，**不许**把参考音频里的原台词
  搬进目标视频"—— 直接关系到音频驱动那条链。
- **官方"标准镜头信息表"六列与 STEP 5.5 强制自检**（`skills/3d-animation-short-generator`）
  完全没进平台：六列 ↔ 我们的字段一一对应，而其中三条自检是可机检的。

**修复**：
- **产出侧**（`internal/director/director.go`）：相机词表按官方三维写法重写 + 切镜措辞与
  "优先运镜" + `summary` 六种任务类型（含我们何时该用 audio reuse / audio reference）+
  `retention_analysis` 官方条目格式与音频标记 + 风格句位置按模式分开 + 参考音频纪律 +
  `subject_definitions` 的官方标签纪律（一行一项、来源引在定义内、`<Subject N> (Sx)`、
  `<Audio 1> is the voice-timbre reference for <Subject 1> (S1).`）。
- **新增 `## SHOT TABLE` 规则段**：把官方六列 ↔ 我们的字段对照写进提示词，并落三条自检
  （钩子密度 / 单镜主要角色 ≤3 / 空间锚点继承）。
- **字段与守门**（`internal/project/shot_table.go`）：新增 `shots[].hook_type`（官方受控词表
  8 项）＋ 契约 4 条 warn：每镜必须有钩子、每连续三镜至少一个 reveal/reversal/callback、
  开篇与收尾必须是强钩子、单镜主要角色不超过 3；场景卡补 `landmarks`/`light_state` **必填检查**
  （官方 STEP 4）。
- **三视图细节板**（`internal/pipeline/board.go` + `prompts.go` 的 `BoardImagePrompt`）：
  按官方 STEP 3 的 production reference sheet 规格（3/4 视图 + 正/侧/背全身 + 6 头角度 +
  6 局部细节）与技能侧 §2.2 的版面要求，**由已通过的定妆照经图像编辑派生**（身份按像素保住，
  绝不重新文生图），产物 `<base>_board.png` 与主图同目录。三条硬约束：身份源不换、
  **不参与镜头参考**（refs 只认主图与转台图）、板上不画字（我们的 T2I 画文字必成乱码字形）。
  触发：人形角色（human/chibi）＋ 板缺失或**比定妆照旧**（定妆照因朝向自检重出过）。
  库关联图后缀集中成 `library.relatedGlobs` 一处（原来三处各写一份，加新后缀必漏一处）。
- **单镜上限维持 10 秒**（用户 2026-09-27 拍板，不做 12/15 秒实测）：依据是负载而非时长 ——
  本地 H3 单镜成本随帧数超线性增长（10 秒 ≈ 6 秒的 2.8 倍）；已写进
  `plan_contract.go` 的 `PlanMaxShotSeconds` 注释，作为"已经定过、别再问"的凭据。

**顺带修掉的两个真实缺口**（"双侧同源"守卫当场抓到）：① 规划轮（真正写 `scenes[]` 的路径）
漏了 `sysSceneRules`；② 同一条路径的 scenes schema 缺 `landmarks`/`light_state`。
另：`portrait_assembly_test.go` 的"装配唯一实现点"守卫拦下了我在 board.go 里手拼取景 ——
板子的装配因此落在 `prompts.go`，并作为**第三个合法装配点**登记（数据与装配分离）。

**验证**：`internal/project/`（视角/尾帧/钩子/连续同景别/场景卡汉字/H3 格式，每条正反双向）、
`internal/pipeline/board_test.go`（版面与取景替换、幂等、横版画幅、归属判据、板子不进 refs、
非 ComfyUI 引擎如实报错、定妆照重出后板子判过期）、`internal/library` 的关联图收集/清理契约
（新增 `_board`）、`internal/director` 与 `plan_contract_ext_test.go` 的双侧同源守卫。
`go test ./...` 14 包全过。

## 技能侧整改单落地：镜头语言层（视角 / 尾帧状态 / 场景卡 / H3 格式）（2026-09-27）

**根因**（依据技能侧 `docs/技能侧交付-平台侧整改单-2026-09-27.md` §1.1–§1.5）：平台直出的分镜在
**镜头语言**上是残缺的 —— `camera` 只有运镜、**零机位角度**（复核实测：最长连续 21 镜同景别）；

  改渐隐渐显＋转场字幕）；`end_state` 禁听觉/氛围/情绪词（判据 `EndStateBannedIn`）。
- **场景卡**：新增 `scenes[].landmarks`（连续性地标）＋ `scenes[].light_state`（光态）＋ 事件隔离

  **装配点兜底**：`pipeline.SceneImagePrompt` 强制带上事件隔离串，并自动清掉卡片里的汉字
  （`project.StripCJK`：整句丢弃优先；整段中文退回逐字删除；清空也不退回原文）——
  契约门只能"提示"，真正保证**渲染输入干净**的必须是唯一的装配点。

## 参考图从未生效：根因是 autogrow 提交键写错（2026-09-27）

**根因**（真机实测 + ComfyUI 0.37.4 源码）：H3 Ref2V 的参考图**一张都没进过条件** ——
提交键的形态不对。ComfyUI 的 autogrow（动态槽位）输入在 API prompt 里只认**「聚合键.模板名」**这种点号键：
`comfy_api/latest/_io.py:1199` 把期望的输入名算成 `finalize_prefix(["ref_images"], "ref_image_0")
== "ref_images.ref_image_0"`，槽位名**必须出现在节点输入里**才会被登记成真实输入，再由
`build_nested_inputs` 按 `.` 还原成 `{ref_images: {ref_image_0: tensor}}` 交给节点。
我们一直提交的是**聚合数组** `ref_images = [节点引用…]`：`_expand_schema_for_dynamic` 找不到任何
expanded 槽位，于是走「所有 optional 都没值」分支（`dynamic_paths_default_value = empty_dict`），
`ref_images` 被填成 `{}` —— 节点拿到空 dict，**既不报错也不生效**。

**实测证据**（同一提示词、同种子，只换参考图）：
- 聚合数组写法：节点收到空 dict，`ref_items=0 / ref_blocks=0`，conditioning 里没有 `minimax_refs`，
  两张截然不同的参考图（年轻男子 / 老妇）产出**逐帧完全一致**（22 帧帧指纹相同）—— 用户报的
  「镜头里的人跟定妆照不像 / 画风跟定妆照不一致 / 改定妆照也没用」就是这个；
- 点号键写法：`ref_items=1 / ref_blocks=1`，conditioning 带 `minimax_refs`、`cross_attn` 随参考图改变，
  packed 序列里出现 1008 行参考段（视频行 RoPE 时间坐标整体后移），帧指纹**完全不同**，
  画面里的人与服装确实跟着参考图走。

**修复**：新增 `internal/engine/comfyengine/autogrow.go` 的 `autogrowKey(聚合键, 模板名, i)`
（注释里写明依据与失效机理），`engine.go`（`ref_images` / `ref_audios`）与 `maskgraph.go`
（局部重绘喂裁剪主体）一律改走它；新增契约测试 `autogrow_contract_test.go` 锁住「必须是点号键、
不得出现聚合键本身、槽位必须指向图里真实节点」，`mask_audio_contract_test.go` 断言同步改。

**顺带推翻两条旧判断**（别再做无用功）：① 本机四个「剪枝 + int8」H3 底模**无罪** ——
同一套权重在点号键下立刻生效，不需要再下 20–40GB 未剪枝权重；② ComfyUI 版本无关 ——
`v0.36.0→v0.37.4` 之间没有任何 H3 ref 路径改动，换版本治不了这个病。
旧文档《参考图未生效-实测》把根因归到「剪枝权重把参考分支削掉」是**错的**，该文档已按实测重写。

**验证**：`go test ./internal/engine/comfyengine/` 全过（新增两条 autogrow 契约测试）；
`scripts/check.ps1` 其余五门通过（前端门在本机经管道捕获子进程输出时会以 `0xC000013A` 收尾，
直接跑 `pnpm run build` 退出码 0、产物哈希不变，属调用环境问题）；
真机端到端对照与复现步骤见 `docs/参考图未生效-实测.md`，探针脚本
`D:\Ai\ComfyUI\_maintenance\mjx-refs-probe.ps1`。

## 定妆照朝向：测出来 + 换种子重出（2026-09-27）

**根因**（真机重出资产后实证）：上一轮把定妆照的正面约束写强了（`fc12ba7`），**但没生效** ——
沈砚那次出的仍是四分之三侧脸。两条实测决定了处置方式：

- **换措辞没用**：把构图声明**前置**到提示词最前面，用固定的 4 颗种子做 A/B（重放 ComfyUI 的
  真实工作流图），A/B 的朝向结果**逐张一致**（3 正面 + 1 四分之三）；朝向由那次采样决定，不由措辞决定。
- **种子是按资产名锚定的**（`nameSeed`，"同名必同图"）：同提示词重跑两次产物**逐像素相同**。
  于是"一次采样偏成侧脸"不会自愈 —— 那个角色**每次重跑都是同一张侧脸**，换项目再建也一样。

**修复**：

- **朝向进自检**（`internal/qc/proportion.go`）：新增 `face_direction` 项（中文名「朝向」），
  与既有的八条比例锚点**共用同一次视觉调用**（只多问一句"是不是正脸"，不多调一次模型）；
  系统提示词写明"四分之三侧/侧脸 = 明显偏离"；判据收在 `qc.FacingOf` / `qc.FacingNeedsRegen`
  两个纯函数里，**"没量到"与"量到且是正面"严格分开**（前者既不当合格、也不触发重出）。
- **未过就换种子重出**（`pipeline/stages_assets.go` 的 `regenerateOnBadFacing`）：只在量到
  **clear** 时重出，种子 = `nameSeed + attempt*101`（同名必同图在重出这条路上被有意打破，
  同种子重出 = 同一张图），上限 2 次（单次失手约 1/4，连失三次约 1/64），每次独立播报，
  用完仍不过就如实告警收手。重出写同一路径 → **刷新内容指纹**。
- **「单资产重新生成」不自动重出**：那是用户手动换一张（随机种子），自动连抽会把一次点击
  变成静默等待；改为如实告知"这张不是正面，再点一次通常就好"。
- **顺带修一个静默降级**：`llm.ChatVision` 的 `max_tokens` 写死 2048，而思考型视觉模型的
  推理 token 也计入 completion —— 推理吃光额度、正文一个字没出就 `finish=length`，
  自检被判"未判定"，**朝向重出根本不触发**。上限提到 8192。

**验证**（真机，逐条可复现）：删掉项目与库里的沈砚定妆照后只跑该资产的资产阶段 ——
第一次出图 → 自检报「朝向 … 实测:头部转向右侧，非正面」→ `↻ 换种子重出第 1/2 次` →
`✔ 定妆照「沈砚」朝向已修正(第 1 次重出为正面)`。目视复核：正面、两眼对称、头顶完整带留白、
胸像取景、国风电影级，外形与锚表逐项一致。新增闸门：`qc` 侧朝向三态与阈值穷举、
`pipeline` 侧源码级钉住重出接线（含"重出必须换种子""指纹必须刷新""regen 不许自动重出"）。

## 交付链路：成片画幅与渲染尺寸解耦 + 字幕安全区 + 去颗粒（2026-09-27）

**根因**：对标红果/抖音的实测（`docs/红果对标-画质配置方案.md`）指出交付口上叠着三笔账，
而且**三笔都不是配置能解决的**：

- **交付分辨率被渲染尺寸绑死**（G1，像素数差 2.01×）：`render.width/height` 一直**同时**驱动
  H3 的生成尺寸与成片的交付尺寸，而 H3 本地渲染的短边上限是 768、平台交付口径是 1080×1920。
  于是"把 768 放大到 1080"这一步谁都没做 —— 留给了平台按自己的算法二次编码。
- **颗粒吃码率、平台还抹掉它**（实测）：film 档那一句 `noise=alls=6` 把同一条 7.29 秒片段的码率
  从 **2.79 Mbps 推到 6.99 Mbps（2.5×）**，而平台二次编码"第一个牺牲的就是颗粒"。
- **字幕压在平台 UI 危险区里**：`MarginV` 写死屏高 8%，而创作者侧口径是字幕要避开底部约 15%
  （进度条与账号条盖在那儿）。

**修复**：

- **交付分辨率与渲染尺寸解耦**（新文件 `internal/compose/deliver.go` + 参数
  `assemble.deliver_width/height`）：成片在终混时缩放到交付档，**缩放在整条滤镜链最前面**
  —— 于是调色（锐化/暗尖/颗粒）与字幕都作用在**交付像素**上，而不是 768 原生像素上
  （P1-3 的"锐化挪到放大之后"随这一步自动成立）。

## v0.37.1 配色收口 + 玻璃效果真正可见(2026-09-24)

**起因(用户反馈)**:「主题配色在各 UI 搭配不够完善需要调整;另外玻璃透明度效果不明显请排除优化处理」。
两条都是真问题,而且都能用**像素说话** —— 本轮全程用"真应用 + 无头浏览器截图 + 像素采样"验收
(见文末"怎么验的"),不靠肉眼猜。

**一、玻璃为什么"看不出来"(根因 + 修法)**
用像素采样对比玻璃开/关,发现每块面板只差 **5~8/255**,肉眼几乎无感。两个原因:
1. **背后没有东西可糊**:页面底色是近乎纯黑的 `--mx-bg1`,所谓氛围光斑只有 6% 不透明度 ——
   一片平滑渐变被 blur 糊完还是那片渐变,自然看不出;
2. **方向反了**:主题的面板色(`--mx-panel-bg` = bg2)本来就**比背景更亮**,把面板变半透明
   只会让它更暗 —— 采样确认"开玻璃反而更暗",这跟"通透"的直觉正好相反。

修法(三件):
- **氛围层重做**:把氛围渐变从 `html/body/#app` 的 background 搬到 `body::before` 的独立图层
  (关键:`#app` 必须透明,否则它的底色会盖住 `z-index:-1` 的伪层——这处一开始就踩了),
  三层大色块 + 一层细点阵/斜纹(blur 抹平的正是高频细节);光斑不透明度 6% → 46/34/26%,
  并新增 `--mx-glow3`(第三色相),背景这才真的有颜色、有结构;
- **材质焊进变量**:玻璃的"白纱"(顶亮底暗一层白)直接拼进 `--mx-panel-bg` / `--mx-panel-bg2`
  的值里,而不是靠 `[data-glass=on] .xxx` 逐个点名 —— 变量在哪儿用、玻璃就在哪儿生效
  (旧写法漏了书卡/日志条这类,质感不统一);实测面板差值 **6 → 12.7~22/255**;
- **配件**:边缘高光 + 投影 + `backdrop-filter: blur(20px) saturate(1.5) brightness(1.15)`,

① 视觉模型 OCR 逐字读出印刷色值;② 像素采样该卡片 4 个色块的实际 RGB。

奶油金青 / 晴空粉霞 / 鸢尾蓝调 / 薄荷落日 / 珊瑚冰川 / 烬海蓝焰 / 柔粉兰紫 / 蜜桃湖蓝,

**推导规则(数据落在 themes.js,规则写在文件头)**:
- `deep` = 4 色里最暗的那个 → 决定背景色相(低饱和 + 4 档极暗亮度,保持暗色 UI 质感);
- `accent` = 从其余 3 色里选,先做"可用化"(饱和度/亮度夹到按钮可用区间);
- **8 套强调色是一次全局最优解**:穷举 3^8 组合,最大化 8 个强调色之间的最小成对 ΔE(CIE76),
  并列取更鲜艳的一套。**为什么不能逐套各挑"最好看的"**:实测那样 8 套里有 6 套都落在金/橘上
  (这些海报的中段色偏暖),主题之间根本分不出来;全局解把最小 ΔE 从 ~6 提到 **24.7**;
- `amber-hi`/`amber-deep` = accent 同色相加亮/压暗 —— UI 里它们是
  `linear-gradient(amber-hi → amber-deep)` 的两端(主按钮/进度条/激活态),必须同色相,
  否则会出现"粉→青"这种跳色渐变;
- `cyan`/`purple` = 剩下两色按与 accent 的色相距离分配;
- **对比度强制下限**:text/bg2 ≥ 16、text2 ≥ 4.5、text3 ≥ 3.0、onAccent↔amber ≥ 5.3、

- green/red/yellow **语义色固定不随主题变**(成功/失败/警告必须一眼认得出,旧 6 套本来也共用同一套绿红黄)。

**顺手修掉的三处真隐患**(主题一换就会暴露):
1. **62 处硬编的旧主题色**:`style.css`/`theme.css`/两个组件的边框、辉光、hover 底色里写死了
   `rgba(255,180,84,…)`(旧琥珀)与旧青/紫 —— 换成蓝或紫主题后这些高亮**仍然是橙色**。
   全部改成 `color-mix(in srgb, var(--mx-*) N%, transparent)`(与 rgba 同语义:预乘插值下
   `mix(C P%, transparent)` ≡ `rgba(C, P/100)`),高亮自此跟着主题走;
2. **`--mx-glow-amber` 一直没被主题覆盖**:主题卡选中框用它的辉光,而 6 套旧主题都没定义,

3. **`:root` 的默认值 = 旧琥珀主题**:JS 应用主题前的那一瞬(首屏)会是旧配色。已把 `:root`
   改成默认主题(极简墨黑)的镜像,并同步更新了 `var(--mx-*, #旧hex)` 兜底色。

**存量偏好迁移**:localStorage 里可能存着已删除的主题 id(如 `midnight-amber`)。新增
`DEFAULT_THEME_ID` / `themeById()` 单一真源:`applyTheme` 解析不到就回落默认**并把偏好改写**,

  不信模型自己的汇总字段。三处调用方(资产阶段/渲染前补齐/资产库「补全多视角」)共用
  `TurnaroundVerifier`;没配 VLM 时跳过校验并如实写日志,不假装校验过。

**③「配音不完整」——三段各自独立的原因**

- **台词装不下镜头**(分镜侧):20 字普通话约需 4.4 秒,落在 4 秒镜头里必然说一半被截。
  新增 `director.FitDialogueDurations`:存盘前逐镜按 4.5 字/秒 + 收尾核算,**只加长不缩短**
  (最多到 10 秒),抬到顶仍装不下的如实报"建议拆镜"。提示词侧同步写死这条算术规则。
- **切在字上**(合成侧,最隐蔽的一条):叠化转场必须让出与画面重叠等长的音频,旧实现固定
  砍在重叠区中点 = **每镜头尾各砍 0.25 秒**;台词常压在镜头头尾,于是每镜都被切掉一点,
  听起来就是"话没说完"。新增 `internal/audio`(RMS 包络 + 自适应门限 + 接缝切点求解,
  纯函数、独立可测),把让出去的这段尽量落在**静音**上;两镜都可裁区间内全人声时自然退回中点。
  实测 3 镜夹具 2/2 接缝完全落在静音。
- **音轨比画面短**:规范化那步改为 `apad + -shortest`,每镜音轨先补到与画面等长 ——
  否则按画面时长裁音频会越界。并新增质检项:实测人声时长 < 应有台词时长的六成 → 告警
  「疑似配音不完整」(机械可判,重渲大概率复现,真正要改的是台词长度或拆镜)。

**③「有杂音」——三道来源分头处理**

- 拼接嘶声/爆音:硬切路径旧实现走 demuxer `-c copy`,AAC 每段自带的 ~1024 采样 priming
  会在接缝处变成缝隙(每刀"咔"一下)。改为视频流复制、音频用 concat 滤镜重建
  (`aresample=async=1` 拉直时间轴),中间轨一律 **flac/mkv 无损**,不为拼接多付一次有损压缩。
- 响度抽气:单遍 loudnorm 是逐帧动态调增益,对话与静音之间会"抽气"。改为**两遍法**
  (measure → `linear=true` 应用),滤波器链逐级回退,缺滤镜时降级而不是整片失败。
- 底噪/嘶声:新增**音频净化**链(`highpass=f=70` + `afftdn`,参数保守),`assemble.denoise`
  未表态即开。H3 自己写在音景里的持续环境声压不掉 —— 那靠分镜侧的音景纪律(提示词新增:
  音景只写 1-2 句安静的底噪,不堆叠声源、不要持续重噪声)。

|---|---|

| 新增单测 | `internal/audio`(包络/门限/切点求解,含"必须落在静音"与"全人声退回中点")、`internal/director`(台词预算与拆镜告警)、`internal/pipeline`(画风块正负词互斥、真人风格被覆盖、默认值语义) |

## v0.34.3 exe 文件属性修复(2026-09-24)

**现象**:打包出来的 `ManJuX.exe` 右键「属性 → 详细信息」整片空白 —— 产品名、版本、公司、
版权、说明一个都没有。`build.ps1` 的注释写着三处版本同源就是为了让"exe 文件属性"正确,
所以这属于既定意图没落地。

**根因**:不是版本没同步,而是**资源块的语言键**。wails 自带的 `build/windows/info.json`
把 StringFileInfo 写在语言 `"0000"`(中性)下,而 Windows 的版本 API(`VerQueryValue`,
也就是资源管理器属性面板用的那条路径)不认这个键,于是整块读不出来。
证据链(避免误判,逐层验证过):

1. `wails build` 日志有 `Generating application assets: Done.`,且用文件监视抓到了它生成的
   `ManJuX-res.syso`(7080 字节,位置正确在项目根、随即被 wails 删除);
2. 直接解析该 syso:CompanyName / ProductName / ProductVersion(0.34.2) / LegalCopyright /
   Comments 全部**有值**,`VS_VERSION_INFO` 结构存在;
3. 在 exe 字节流里 UTF-16LE 搜 `VS_VERSION_INFO`、`ManJuX 短视频创作工作台` 也**都能搜到**
   —— 说明资源确实链进了二进制;
4. 但 `FileVersionInfo.GetVersionInfo()` 读出来全是空 → 所以问题只可能在语言键。

**修法**:`build/windows/info.json` 的语言键 `0000` → `0409`(en-US,通用回退),
并补上 `FileVersion` 字符串与 `fixed.product_version`(原先只有 `file_version`,
且 `0.34.2` 三段版本经 `Sscanf("%d.%d.%d.%d")` 只能解出前三段)。
`build.ps1` 里加了注释说明"同步三处只是必要条件、info.json 才是充分条件",
并在用脚手架重新生成该文件时会踩回来的地方写明要改哪两处。

**验证**:重建后 `GetVersionInfo` 全部字段可读 —— ProductName / ProductVersion /
FileVersion / FileDescription / CompanyName / LegalCopyright / Comments 与 `wails.json`
的 info 块逐项一致。

## v0.34.2 放大链路补齐 LTX 视频 VAE + 权重体检(2026-09-24)

**起因(用户报「LTX VAE 缺失,ltx 放大这条路在本机跑不通」)**:上一轮把 2× 放大端到端接通了,
但只对 **帧级(esrgan)** 那一半做了真机验证;隐空间那一半本机**从来没有跑通过**。深挖后
发现不是一个缺口,而是两个叠在一起:

1. **缺配套的 LTX 视频 VAE**。链路上的 `ltx-2-spatial-upscaler-x2-1.0` 权重早就装好了,
   但 `VAEEncodeTiled`/`VAEDecodeTiled` 还要一个 LTX 视频 VAE,本机 `models/vae/` 里只有
   H3 的音频/视频 VAE 与 Qwen 的 —— 缺的正是 LTX 那一个。
2. **界面选「隐空间」时权重名没跟着换**(真 bug)。`UpscaleOptions.ModelName` 的含义随
   `Type` 而变:ltx 要去 `latent_upscale_models/` 找、esrgan 要去 `upscale_models/` 找。
   而前端只送 `type: 'ltx'`,后端沿用 `DefaultUpscaleOptions()` 的 `4x-UltraSharp.safetensors`
   —— 于是隐空间加载器拿着帧级超分的文件名去自己的目录里找,**连权重都注定找不到**。
   也就是说这条路即使把 VAE 装上,也还是跑不通。

**修复**:

- **补装 VAE**:`LTX2_video_vae_bf16.safetensors`(2331.7 MB)装入 `shared/models/vae/`,
  与 LFS oid 逐字节校验一致。选它而不是同仓库的 `LTX2_video_vae_old_bf16`,依据是作者自己的
  说明("初始蒸馏权重里的视频 VAE 一直是错的,现已换成正确的那个,细节更好");
  并实测确认它命中 `sd.py` 的 `lightricks ltxv` 分支、`latent_channels=128`、带
  `per_channel_statistics`(`LTXVLatentUpsampler` 必需)且 encoder/decoder 齐全。
- **默认参数改为按方式成套**(`engine.UpscaleOptionsFor`):换 `Type` 必定同时换权重名与 VAE 名,
  不再存在"只换一半"的组合。默认文件名(含 ltx 的 VAE)经 `GET /api/meta` 下发给前端回显,
  前端不再自己记常量,用户也就不必再手打文件名(手打的既没校验、打错了也查不出来)。
- **新增放大链路的权重体检**(`comfyengine.UpscaleAssets`,与 `Preflight` 的节点体检互补):
  提交前向 ComfyUI 问 `VAELoader.vae_name` / `LatentUpscaleModelLoader.model_name` /
  `UpscaleModelLoader.model_name` 三个 combo 输入,缺哪个文件直接点名并给出**该放进哪个目录**,
  而不是让用户等一场长任务再收到一句听不懂的节点输入报文。引擎不可达时返回空
  (与 `Preflight` 同一条原则:连不上 ≠ 资产缺失)。

**真机验证时又挖出两个更隐蔽的 bug(都是"假成功",比报错更糟)**:

- **③ `ExtractFiles` 把输入素材当成产物**:放大图的根节点是 `LoadVideo`,而 ComfyUI 会把
  **从 input 读到的文件**也报进该节点的 outputs(同样带 `animated` 标志)。`Upscale` 取
  "第一个 animated 文件",而 `outputs` 是 map、遍历顺序随机 —— 一半概率把**源片原样**
  下载回来并提示"2× 放大完成"(实测:分辨率 320x192、字节数与原片完全相同)。
  上一轮只验到"接口返回 200 + 有文件落盘"就以为接通了,正是这里漏掉的。修法:产物必须
  是**做出来的**而不是**传进去的** —— `ExtractFiles` 排除 `type == "input"`;
  同时补 `TestExtractFilesSkipsInputs`(跑 30 轮防 map 顺序侥幸)、`TestExtractFilesNoSaver`
  (只有输入节点时返回空,让调用方明确报"未找到视频产物"而不是假成功)、
  `TestExtractFilesStillFindsImage`(出图链路不受影响)。
- **④ `ComboList` 只认旧式 combo schema**:ComfyUI 的 `object_info` 里 combo 有两种形态 ——
  旧式 `[["a.safetensors",…], {…}]` 与新式 `["COMBO", {"options":[…,…]}]`。原实现只解析
  `def[0]` 当字符串数组,于是新式节点一律返回 `ok=false`;而调用方普遍把 false 理解成
  "节点不存在/输入已改名" —— 权重体检刚上线就会把"权重装好了"误报成"节点缺失",把一个
  真实可用的链路说成坏的(实测 `LatentUpscaleModelLoader` / `UpscaleModelLoader` 都是新式)。
  修法:两种形态都解析;补 `TestComboListBothSchemaShapes`(报文取自本机 ComfyUI 0.35.1 真实响应)。

**真机实测结果(本机 24GB 卡 / ComfyUI 0.35.1)**:

| 源片 | 帧级 esrgan | 隐空间 ltx |
|---|---|---|
| 320x192 / 60 帧(合成图) | 12.2s → 640x384 | 6.0s → 640x384 |
| 1344x768 / 48 帧(真实漫剧镜头) | 183.1s → 2688x1536 | 18.3s → 2688x1536 |

两条都满足:精确 2×、时长零漂移、音轨保留。**结论纠正了一个此前的想当然**:帧级并不比
隐空间快,反而是隐空间快约 10 倍(逐帧 4× 超分要在像素域过 512 瓦片再收敛回 2×);
隐空间的代价是学习式视频 VAE 会抹软**硬边细字**(片内字幕、路牌小字实测被糊),
而真实漫剧画面的纹理(布料、缝线、材质底板)明显优于源片。据此改了界面标签与提示文案
(原写"帧级 快且稳 · 推荐"与实际相反),并在 `docs/使用手册.md` 列出对照表与选择建议。
另核实一处非隐患:`ImageUpscaleWithModel` 内部按 512 瓦片处理、OOM 时自动减半(最低 128),
768P/48 帧实测无溢出,不需要额外做分块。

**测试**:新增 `TestUpscaleOptionsFor`(锁"按方式成套",防第 2 个 bug 回归)、
`TestUpscaleAssets`(假 ComfyUI 覆盖"齐备/缺 VAE/缺权重/节点缺失/文件名空白/引擎不可达"六种情形)、
`TestHTTPContractMetaUpscaleDefaults`(meta 必须下发放大默认值);
另加一条**默认跳过**的真机测试 `TestLiveUpscaleRoute` —— 图契约测试证明不了"这台机器上的权重够不够",
更证明不了"产物是不是真的被放大了"(bug ③ 就是这样漏过去的),
这类缺口只能对着真引擎验(设 `MANJUX_LIVE_COMFY` 与 `MANJUX_LIVE_SRC` 即启用,
断言精确 2× + 时长零漂移 + 音轨保留)。

自 `fef0c97` 起就没有 `##` 标题,挂在文档前言下面 —— 补上标题使其成为正常条目;

- **秒级建集快路径**(用户「一章一档还需要慢慢拆集?」):章界/章名/原文全部已知时,"拆集"不需要 LLM —— 平台直接建集(实测 **3 秒建 64 集**、产线同秒开跑),LLM 只在后台**并行补写**各集剧情节拍 brief(brief 独立上下文、3 路并发,写完回填 source 的【本集剧情】与【前情提要】;实测 0 失败)。之前"分段等 LLM 拆集"要数分钟才出第一集。
- **覆盖核对与自动补缺改读真源**:集覆盖章号在拆集时**落盘**到 `Project.Chapters`,核对与补缺都以此为准(其次才是原文章头,最后才是 LLM 字符串)。

## 未发版 · 人物一致性事故根因修复(2026-09-12,用户「定妆照/多位图/视频渲染的人物一致性去哪了?」)

**现象**:同一角色三张脸 —— 定妆照是圆软脸大眼睛的俊美版,而视频渲染出来是长脸细眼、很符合角色卡的另一个人;多位图(转台图)又与两者都略有差别。

**根因(两条,都在"我改过的地方")**:
1. **风格块改写面部特征**:`styleExpand` 的 3D/BJD 分支里写着 `large glossy stylized eyes`(大而有光泽的风格化眼睛)。用户钦定的主风格是"次世代3D·BJD虚拟人",于是所有角色定妆照都被强制画成大圆眼、圆润脸 —— 与角色卡里的面部描述**直接对打**:江砚写的是"清瘦,长脸窄下巴,眉骨略高,细长单眼皮、眼神沉静冷厉",却被画成圆脸大眼。而定妆照是全片锁脸的锚:它一偏,视频(按文字渲染)与多位图(按定妆照转身)就永远对不上。**这是我上一轮"风格具象化"埋的雷**。
2. **参考图契约与实际不符(自伤)**:上一轮我把"参考图去冗余"设成默认开,并把提示词契约改成"每角色一张图";而拼合转台图被模型缩放到入口分辨率时,每格只剩约 1/4 像素,锐利的脸被摊薄 —— 实测只喂拼合图后,渲染出来的角色**服装道具照抄得很准、脸却变成"另一个更俊美的版本"**。回退时又发现契约仍在说"一张图",与实际的"定妆照+转台图两张"矛盾,会诱导模型认错参考图。

**修复**:
- `styleExpand`:删掉**一切形状类词汇**(`large glossy stylized eyes`);风格只描述材质与渲染方式(表面/光泽/媒介),并新增 `identityFidelityBlock()` 硬约束:脸部必须与文字描述逐项一致(脸型/下巴/眼型与眼皮/眉形/鼻形/发长),风格只改渲染表面、**不得**美化或放大眼睛或柔化下颌或让角色变年轻变帅。这条只作用于角色(styleExpand 只在角色路径追加),不动场景图;
- 参考图去冗余**回退为默认关**(显式开才生效),参考图契约恢复为"角色可能占两张图(定妆照 + 转台图),按内容识别、脸以定妆照为权威",并同步 `sysH3Format` 的编号规则与 retention 说明;
- **同剧对比块补一句"名单不许画出来"**:实测不点明时,模型会把名单里的其他班底当画面元素塞进角落(郑伯的定妆照里出现了小尺寸的卫东与 Q 版江砚)。

**真机验证(A/B,同一角色同一镜同 seed)**:
- 定妆照:修复前=圆软脸大圆眼(偏离描述);修复后=**清瘦长脸、细长单眼皮、长脸窄下巴**(与角色卡逐项一致);其余 5 个角色一并重生成,卫东(壮实方脸/寸头/浓眉小眼/黑制服挂对讲机/指间夹烟)、郑伯(佝偻瘦削/长脸深皱/花白发/抱蓝布包)、老赵(秃顶圆胖/络腮胡茬/蓝工装挂钥匙)、阿贵(瘦小圆脸偏黑/黄T恤围裙蒲扇)均与描述吻合;
- 视频渲染:用修复后的定妆照重渲第01集镜 1 —— 渲染帧与新定妆照**同一张脸**(长脸细眼、乱短发、同款灰蓝工装与领口镊子),一致性恢复;
- 多位图:清掉 6 个角色的旧派生角度图后按新定妆照重出(转台图第 1 格即新定妆照,其余格为同一人的转身角度)。

**审计结论(为免再犯)**:本轮把"风格"与"身份"彻底分离 —— 风格块只能改渲染表面,身份只由角色卡文字 + 定妆照决定;任何"让画面更好看"的词汇若涉及形状(眼/脸/下颌/发长),一律不得进提示词。

## 未发版 · 渲染资源治理(2026-09-12,用户「渲染时 GPU 和内存快爆了」+「该释放的就释放,专职某一项」)

**量化现场(同镜 18:7 秒/192 帧/8 步,单管线)**:显存 **23529/24463 MiB(96%)**、ComfyUI 的 python 进程独占 **40.3GB**、系统内存峰值 **61.0/63.6GB(96%)**、采样 **91.6 秒/步**(日志 `12%| 1/8 [03:02<11:12, 96.04s/it]`)、单镜 **819 秒**;ComfyUI 日志明确写着加载 H3 时 `0 models unloaded` —— TE(15GB)没有被卸载,与 H3(20GB)一起挤 24GB 卡,每步都在搬权重。

**排查过的四条路(用实测排除,不猜)**:
- 加载模式:动态显存(--disable-dynamic-vram 经典模式)= 101.9 秒/步,**更慢** → 不是动态显存的问题;
- 模型共存:--disable-smart-memory 后仍 91 秒/步 → 不是共存的问题(但它确实把 TE/VAE 及时卸掉,内存峰值从 61GB 降到 43GB);
- 缓存:--cache-none(ComfyUI 日志 `Disabling intermediate node cache.`)→ 内存显著下降,速度不变;
- 结论:步速不是内存病,而是 H3 在 192 帧/768×1344 下的注意力计算量本身。

**官方文档的两条硬信息(ComfyUI 官方 H3 教程 + 本机源码核对)**:
1. H3 原生画布就是**短边 768**(1344×768 约 0.98MP),并且"1.0MP 档会得到 1376×768,超出模型 768×1344 的面积上限" → 我们用的 768×1344 已经是官方允许的上限,画质上没有可让的空间;
2. **官方唯一推荐的提速手段是 Sage Attention**:教程原文「可以将生成速度大约提升一倍」,且画质损失极小;可用 `--use-sage-attention` 全局启用,或用 KJNodes 的 Patch Sage Attention 节点局部启用。官方同时说明需按 PyTorch/CUDA 版本安装对应的 sageattention 轮子。

**落地(实测数据)**:
- 装上与本机完全匹配的官方推荐轮子 `sageattention-2.2.0+cu130torch2.10.0andhigher.post6-cp310-abi3-win_amd64.whl`(post6 修掉了旧版的"黑图/噪点"越界 bug —— 2026-09-10 用户报的"同内容变差"很可能就是旧版该 bug,这次用的是修复版);
- 启用后同一镜:**44.8 秒/步(2.04 倍)、单镜 819 → 432 秒、显存峰值 96% → 92%、内存峰值 61.0 → 46.2GB(96% → 73%)**;产物逐帧目检无黑图/噪点、人物连续;
- 接入方式:`comfyLaunchArgs(main, port, reserveVRAMGB, sage)` 纯函数组装启动参数(单测 `TestComfyLaunchArgsMemoryFlags` 钉住),Sage 采用**三态开关** `ComfySettings.SageAttention *bool`:nil=装了包就自动启用、显式 true/false=用户开关(设置页「Sage 注意力加速」),且**只有检测到 standalone-env 里确实装了 sageattention 才加该参数**(没装就加会让 ComfyUI 直接报错);
- 官方语义参数替换:`--reserve-vram` 换成本版的 `--vram-headroom`(官方说明:让 DynamicVRAM 把这些显存完全留空、**连别的程序占的也算**),对应设置页「显存预留(GB)」;
- 参数不含画质开关:`--fast`/`--use-ck-attention`/`--use-flash-attention` 一律不出现(2026-09-10 用户实证画质劣化后撤下,测试里钉死)。

**「该释放的就释放,专职某一项」(用户定调)**:管线收尾(成功/失败/停止)自动释放显存并如实播报 —— 实测日志 `🧽 管线结束:显存已无占用(当前 1.4 GB)`(1.4GB 是桌面与其它程序的占用);一次性 GPU 操作(抽卡/自定义新建/库资产重抽/补全多视角/局部重绘/音频驱动/单资产重生成)完成后同样释放,**但带两道护栏**:①任何管线在跑时不释放(那块 GPU 正在被管线使用);②ComfyUI 队列非空时不释放(`/free` 会卸载模型,若那条任务正在执行,权重会被踢出显存、随后每步重新流式加载等同白跑)。"释放显存"的前后对比也修了 —— 旧实现卸载后立刻读数,永远显示 22.3 GB → 22.3 GB(用户据此以为这步是假的),现在轮询最多 5 秒取真实降幅,没降就照实说"引擎无可卸载的常驻模型"。

**单镜负载引导**:资产/渲染的负载随帧数超线性增长(10 秒镜 ≈ 6 秒镜的 2.8 倍),剧本提示词从「每镜 4-10 秒」收紧为「每镜 4-8 秒(整数);需要更长的叙事请拆成两个镜头,不要把一镜拉长」。

## 未发版 · 身份一致性与台词语言治理(2026-09-12,用户七项报障)

**主线根因:提示词让"文字描述"压过了"参考图"**。旧锚定块写的是「外貌描述优先级最高,任何画面细节与之冲突时以此为准」——等于明确告诉 H3「忘掉参考图那张脸,按文字重画」。定妆照由 Krea-2 按另一套提示词自由创作,视频再按文字自由创作一次,两次彼此独立,于是:脸趋同、文字里有痣/红鼻头就画出来而定妆照没有、定妆照与视频/多视角对不上。本轮以「定妆照就是本人,文字只许管服装道具动作」为主线重排。

**① 配音混入听不懂的"鸟语"**:根因——H3 靠 `<d>…</d>` 内的语言标记决定用哪种语言说话,提示词模板要求写 `<d>[Chinese]台词</d>`,但 LLM 直出时标记经常丢(实测第01集旁白全是 `<d>断的、折的、锈的…</d>`),模型拿不到语言线索就自己猜。修法——代码级兜底 `EnsureChineseDialogue`(先把 `<d>[任意语言]` 归一成裸 `<d>`,再统一换成 `<d>[Chinese]`,末尾追加一条 `MANDARIN ONLY` 强制语言规则;幂等,且不碰无台词的镜头),接入点四处:剧本阶段**存盘前**(新方案一次修好)、渲染阶段(老方案兜底)、2K 重生成、局部重绘/音频驱动;技能侧同步在 `sysHard` 点明「[Chinese] 标记是必填,写了它才会说普通话」。测试:`TestEnsureChineseDialogue`(补标记/换语言标记/幂等/无台词不追加)。

**② 多级弹窗层级异常**:根因——Element 的弹层计数器从 `2000` 起、每多开一层 +1,而全屏媒体预览器(`MediaViewer`)的遮罩也写死 `2000`:从「资产库详情」「分镜卡」这类弹窗里点图放大时,预览器被压在弹窗底下(看不见、点不到)。修法——遮罩改 `2700`(高于弹层计数器与运行日志悬浮窗 2600,低于永远最高的 Tip 3000),并在注释里写清这个层级约定。

**③ 相同角色无中生有多生成定妆照(名称一致与不一致都有)**:根因——库里按**名字精确匹配**,而分集分镜由 LLM 独立撰写,同一角色换个称呼很常见:实测同一本小说里机关人在 第01集叫「机关人（一三七四一号）」、第02集叫「阿枢（一三七四一号）」、第03集叫「机关人（一三七四一）」,肩上小人也有「肩上小人/阿枢肩上小人/机关人的肩上小人」三种叫法 —— 结果 19 个库条目里至少 5 个是同一个人的分身,每个人还各出一张定妆照。修法——新增 `Library.Find`(名字精确 → 名字归一化(去空格/标点/「的」/「号」/括号内容)→ 别名表 → 名字互为前后缀且描述相似度 ≥ 0.6 → 描述相似度 ≥ 0.8),命中即复用并在库里**登记别名**(下次按名秒级命中,详情弹窗会显示"同一角色的其它叫法");置信度不足一律不合并(宁可多生成一张,也不能把两个角色并成一张脸);资产阶段的复用播报会说明"已按「X」的定妆照复用"。技能侧同步强化系列锚定文案:点名「同一个人可能以名字/代号两种称呼出现,判定为同一人就必须共用同一张角色卡」,并在 `sysHard` 写死「ONE character = ONE card」。测试:`TestFindMatchesSameCharacterUnderDifferentNames`(四种叫法都命中同一条目 + 别名持久化 + 不同角色不得误并)、`TestNormNameAndDescSimilar`。

**④ 人物脸部相似**:根因同上(视频按文字重画,而"五十来岁老人"这类文字把不同角色的脸拉到一起);修法——锚定块改为身份锁(见主线条目),技能侧把"每镜复述五官特征"改成"复述服装/道具/姿态/状态",并声明「有参考图时脸以参考图为准,文字不得添加参考图没有的面部标记」。测试:`TestAnchorPromptLocksIdentityToPicture`(旧文案必须消失、身份锁/照抄参考图/禁止新增标记必须存在、描述仍保留但用途受限)。

**⑤ 定妆照没有的痣,视频里"无中生有"**:两处根因——①LLM 会给角色**自行发明**原文没有的标记(张屠的"嘴角边一颗黑痣"在原文里查无此事,151 处"痣"全部来自另一本书);②即便描述里有,定妆照(832×1248 半身)也常常画不出米粒大的痣,而视频按文字补上 → 两边不一致。修法——技能侧 `sysHard` 增「外貌事实只能来自原文,不得发明痣/疤/胎记/红鼻头/特殊发色」;平台侧身份锁显式禁止"添加参考图里没有的面部标记"——定妆照没有的,视频不会再长出来。

**⑥ 定妆照与多位图角色不一致 + ⑦ 多位图出现小红鼻/小红脸**:根因——转身视频提示词把定妆照的文字描述整段塞进 `subject_definitions`(描述里的"圆钝的小红鼻子"被当成绘图指令补了出来,而定妆照本身没有),同时 "character turnaround reference" 在训练数据里大量对应**角色设定图**,模型自作主张换画风/换体型:实测张屠(成年胖脸差役)的转台图第二帧起变成红脸蛋的大头娃娃。修法——`turnaroundPrompt` 重写:①`compactIdentity()` 从定妆照提示词里剥掉**面部/皮肤类词汇**(rosy/blush/red nose/mole/nose/eyes/face/skin… 一律不传给转身提示词)与构图要求,只留年龄/性别/服装锚点;②四帧锁同一景别(旧版只对第 1 帧说了上半身中景,后三帧模型自由拉到全身);③加一组"必须照抄、不许重设"的硬约束(道具同色同形、无新增文字、体型与画风不变)与 NEGATIVE 段**按参考图**表述(成年人保持成年、本就是娃娃体的角色保持原样)——注意这句最早写成绝对"no chibi",会与"照抄参考图"打架,已改为"体型以参考图为准";④注释里记下一条血泪经验:负面句里点名某个特征会把它画出来(写"no grey hair"反而长出长银发,实测),所以一律用"照抄参考图"的正向表述。测试:`TestCompactIdentityStripsFacialWords`(面部词剥离 + 服装/发型锚点保留)。

**顺带**:`stripComposition` 升级为 `compactIdentity`(同一个函数名保留语义更清楚的版本);资产阶段的多视角写回、渲染前补齐、库内一键补全都走同一份转身提示词,三处同时受益。

## 未发版 · 管线生产合理化(2026-09-12,用户「管线生产需要合理化,别老是出现失败」)

**出图/渲染超时口径:排队等待不再计入执行预算**。根因——`WaitForDone` 旧实现把 deadline 定在"提交那一刻"(`time.Now().Add(timeout)`),于是排在前面的长视频任务(单镜可跑数十分钟)会把后面所有任务的超时预算一起吃光:定妆图兜底上限 10 分钟,排 10 分钟队就**必然**被判「渲染超时(单镜上限 10m0s)」,而引擎其实完全正常。实证:第03集三张角色定妆照(机关人（一三七四一）08:24:28→08:34:28、程墨的肩上小人 09:10:47→09:20:47、卫戎 09:20:47→09:30:47)与第02集场景图「库外土路·泥沟」(07:47:45)全部**精确卡在 10 分 00 秒**被杀;同一时段不受排队影响的生成(卢掌案 7 分 15 秒、机关人的肩上小人 2 分 15 秒)则正常成功。后果不只是那几张图:角色定妆照缺失 → `镜头 N 缺 1 张参考图(char_azhu)` → 该镜降级 t2va,**角色锁脸完全失效**。修法——新增纯函数 `DecideWait(now, submitted, execStart, execTimeout, queueCap)`:执行预算从"首次观察到正在执行"起算(`timeout` 只作卡死防线),排队另有独立的 90 分钟上限 `queueWaitCap`,超时错误分层报(`已执行 X,执行上限 Y;排队等待 Z` / `排队等待 Z 仍未开始执行,排队上限 Y;通常是前面压着更长的视频任务`);进度文案同步改成「排队中 · 已等 X 分」/「执行中 · 已 X 分」,用户一眼看出慢在排队而不是卡死。测试:`TestDecideWaitQueueDoesNotEatExecBudget` 四种情形(排队 25 分钟不算超时 / 排队 25 分钟+执行 5 分钟仍放行 / 执行 11 分钟判卡死 / 排队 91 分钟报排队超时);`TestWaitForDoneUsesConfiguredTimeout` 改为两段式(排队中 1 纳秒上限也不得判超时,执行中 1 纳秒上限必须包装 `ErrRenderTimeout`)—— 顺带发现旧测试的 `/queue` 造数用了字符串序号,会被当成"旧版 id 形态"取走,已改成真实形态 `[[1,"pid-1"]]`。

**全局单管线铁律**:根因——`Coordinator` 只按项目去重(`runs[projectID]`),不同项目可以同时启动;多集并发共用**一张显卡**不是"更快"而是互相伤害(出图任务排在长视频任务后面排队被超时杀掉、单镜从 3-5 分钟涨到 19-26 分钟,即代码里记过的显存反复换入换出)。修法——`Start` 在项目去重之后加一道全局检查:已有别的项目在跑就明确拒绝,错误信息写清代价(实测哪两件事会变慢/失败)与出路(先停它再启动)。测试:`TestStartRefusesConcurrentPipeline`(同项目重复启动报"正在运行"→ 有他项目在跑时拒绝且理由含"显卡"→ 放开后必须放行到项目校验)。顺带核对:`pipe.Start` 全仓只有"单项目运行"与"批量产线逐集"两个调用方,没有任何"一次并行跑多集"的功能会被这道护栏误伤。

**批量产线等待策略:看产物进展,不看跑了多久**。根因——旧实现用固定 2.5 小时上限判断"这一集跑完了",超时即当完成开下一集,而**该集仍在运行**;`Result()` 对仍在跑的项目返回空串,既不等于 `ResultStopped` 也不等于 `ResultFailed`,于是直接落到「✔ 批量产线 N/M:完成」分支 → 上一集还在渲染、下一集已经开跑。日志里的时间差是精确的:第01集 03:10:44 起跑(09:38:09 才结束,耗时 6h27m25s)→ 产线 05:40:44 记"完成"(正好 2h30m);第02集 05:40:44 起跑 → 08:10:45 记"完成"(正好 2h30m),而它当时仍在渲染。修法——①等待改成活性驱动:`projectFreshest` 取项目目录内最近一次产物改动(跳过 logs/),只要有新产物(定妆照/转台图/manifest 状态/镜头 mp4/成片)就一直等,连续 `batchStallLimit`(60 分钟)毫无变化才判卡住并暂停产线;`batchEpisodeHardCap`(12 小时)为绝对兜底——角色多、转身多的集本来就慢(实测一集 10 个角色光转身就约 50 分钟),固定时长上限必然把"慢而正常"当成异常;②绝对兜底到点而该集仍在运行时,同样**不得**当完成:保留它继续跑,产线停住并明确说明原因与出路(等它跑完再点「批量产线」续跑)。测试:`TestProjectFreshestDetectsNewArtifacts`(新产物刷新活性信号 / 只有日志在动不算进展 / 目录不存在不 panic)。

**资产阶段两阶段化:先出完所有定妆照,再统一出多视角转台图**。根因——旧实现是"一个角色一次来回":Krea-2 出定妆照 → H3 出转身视频 → 下一个角色再 Krea-2 → H3,10 个角色就是 20 次模型换入换出(H3 约 20GB),显存反复腾挪正是"每步 150 秒"的来源。修法——资产阶段拆成两段:`pendingViews` 先在定妆照循环里只记录待办,等所有角色/场景的定妆照(含 Q 版)出完后,再统一跑多视角(H3 只加载一次);多视角写回资产库的动作跟着挪到第二阶段(同一角色全局只付一次转身成本)。顺带修一处不一致:多视角此前在**资产阶段无条件生成**,项目里「角色多视角转台图」开关只约束渲染前补齐 —— 关掉开关也省不掉这段 GPU 时间;现在资产阶段同样读 `ViewsOn()`。真机验证(第03集,4 角色 + 3 场景待补):阶段①七张定妆照每张 12-21 秒**全部一次成功**(上一轮同款任务在并发下全部卡 10 分钟被杀),随后日志「阶段②:多视角转台图 4 个角色」开始批量转身。

**停止不再伪装成「生成失败」**。根因——用户点停止时,资产阶段剩余资产的 Krea-2 调用立刻返回 `context canceled`,旧实现把它逐条记成「生成失败:场景「X」:context canceled」(实测 09-11 与 09-12 共 8 条),并在结尾补一句「缺 N 张参考图,对应镜头将以 t2va 纯文生渲染」—— 用户由此得到"场景也有失败"的错觉,而真相只是"停在这里了、续跑会补齐"(第03集那次:3 张场景 + 1 个角色 = 7/14 缺图,全部是停止导致)。修法——`check()` 在尝试生成前先看 `ctx.Err()`,调用返回取消时不记失败、改记「已停止:X 未生成(续跑时自动补齐)」;结尾若本次运行被取消,只报「⏹ 资产阶段已停止:定妆照已就绪 X/Y,其余 N 个未生成(续跑时自动补齐,不会降级纯文生)」,不再报 ✔、不再预告降级;多视角阶段被中断另有一句「⏹ 多视角转台图已停止:X/Y 完成,其余将在续跑时补齐(定妆照已就绪,不受影响)」。
