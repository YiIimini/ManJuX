# 渲染脚本契约（manjux.plan v1）

> **双侧共组**：技能端 **ManJuNovel**（写小说）与平台端 **ManJuX**（渲染）之间只有一份契约 ——
> 一份 `plan.json`、一张规则表、一个版本号。**谁也不缺谁**：技能端产出前自检，平台端入口再守一遍。
> 技能侧镜像：`~/.dsh/skills/manju-novel/references/渲染脚本契约.md`（改契约必须**两侧同版本号一起提交**）。
> 平台侧实现：`internal/project/plan_contract.go`（规则表）＋ `internal/server/handlers_shot.go::importPlan`（入口守门）。

## 一、分工：各干各的，谁也不猜对方

| | 技能端 ManJuNovel | 平台端 ManJuX |
|---|---|---|
| 输入 | 一本写完的小说（正文 + 设定集 + 数字锚表 + 口径锁定） | 技能端产出的**项目包** |
| 产出/职责 | **拆集 → 角色卡/场景卡 → 镜头切分 → 台词抽取 → 时长预算 → H3 提示词 → plan.json** | 解析包 → 资产（定妆照/场景图，走资产库复用）→ 渲染 → 质检 → 合成 |
| 不该做的 | 不渲染、不管模型/显存/队列 | **不重新发明人设、不重写分镜**（那是技能端的活，它手上有设定集） |

**省掉了什么**：平台原来那一步「LLM 直出分镜」（`PhaseScript`：单集一次深度推理，**2–6 分钟** + token 成本，
且渲染端只拿到一段源文本、要重新猜人设与场景）。改成"技能端直接出脚本"之后，这一步整段消失：
渲染端**从 assets 阶段直接开工**。

**这一步靠什么保证**（`pipelineStages`，2026-09-26 抽出并加门）：全流程（`all`）时若盘上已有有效方案
（`plan.json` 且 `shots` 非空），阶段表里**根本不含 `PhaseScript`** —— 不只是"跑得快"，更是**防毁活**：
重新生成会改写每镜提示词 → 镜头指纹全变 → 已渲的镜头全部作废（技能端交上来的好脚本被平台悄悄盖掉，
然后从零重渲）。只有**显式**指定 `script` 阶段（界面「生成分镜方案」）才重新创作 —— 那是作者推翻方案、
重新创作的唯一入口，不许被"优化"掉。三条用例钉住：已有方案必跳过、无方案必照跑、显式阶段必听。

**换来什么风险（所以需要契约）**：一旦分两侧，就会出现"技能端写出平台端从没见过的东西，
渲染照跑、成片是垃圾，而没人知道该怪谁"。**契约必须可执行**：同一张规则表，两侧各跑一遍。

## 二、项目包结构（技能端产出，平台端原生目录）

包可直接落到 `data/projects/<书名>/<书名·第NN集·标题>/`（Store 的分集命名规则 `^(.+)·第\d+集`）：

```
<书名>/                       ← 系列根（也是 import-package 可接受的入参）
├── _pool.json               技能侧的书级角色/场景池（**跨集 id 稳定：换 id ＝ 换脸**）
└── <书名>·第01集·<集标题>/
    ├── manifest.json     契约声明（技能侧写；平台侧据此知道这是外部产出的包）
    ├── project.json      平台原生项目元数据(id/name/config)，Store 直接装载
    ├── source.txt        本集原文（**带【本集原文】标记** → 平台会启用"沿原文节拍逐段改编"提示）
    ├── plan/plan.json    ★ 契约文件（Plan schema，见第三节）
    ├── assets/           平台产出（characters/ scenes/ props/，技能端**不写**）
    ├── clips/            平台产出（NNN.mp4 + manifest.json）
    └── output/           平台产出（final.mp4）
```

`manifest.json`（技能侧写，平台侧只读）：

```json
{
  "contract": "manjux.plan",
  "version": 1,
  "book": "书名",
  "episode": "第01集",
  "episode_title": "集标题",
  "chapters": [1, 2],
  "episode_seconds": 300,
  "produced_by": "ManJuNovel skill",
  "produced_at": "2026-09-26T10:00:00",
  "counts": { "characters": 8, "scenes": 3, "shots": 44 }
}
```

## 三、`plan.json` schema v1

字段以 `internal/project/project.go` 的 Go 结构为准（**Go 代码是唯一真源**）：

```jsonc
{
  "title": "书名",
  "logline": "一句话梗概",
  "style": "视觉风格（英文，注入每镜提示词）",
  "characters": [{
    "id": "char_shenyan",        // 镜头里用它引用
    "name": "沈砚",
    "kind": "human",             // human/object/spirit_pet/beast/incorporeal/chibi（可空，平台会推断）
    "description": "中文外貌/服装/气质（一致性依据）",
    "image_prompt": "英文定妆照提示词",
    "voice": "英文声线描述（进 H3 提示词）"
  }],
  "scenes": [{
    "id": "scene_street", "name": "临水城菜市口长街",
    "description": "中文场景描述", "image_prompt": "英文场景图提示词"
  }],
  "shots": [{
    "id": 1,                     // 1..N，同时是产物文件名 NNN.mp4
    "scene": "scene_street",     // 必须 ∈ scenes[].id
    "characters": ["char_shenyan"], // 必须 ⊆ characters[].id
    "shot_size": "特写",          // 远景/全景/中景/中近景/近景/特写（同族词如"大特写"也认）
    "camera": "Static, no movement",
    "action": "中文一句话画面动作",
    "dialogue": [{ "speaker": "沈砚", "text": "小本经营。" }],
    "narration": "",             // 旁白（画外音），与 dialogue 一起计入时长预算
    "duration": 6,               // 秒，硬区间 4–10
    "mode": "ref2va",            // ref2va(有参考图) / t2va(纯文生)，空值平台自行推断
    "h3_prompt": "完整 H3 提示词（六段式/三段式），台词段必须是 <d>[Chinese] … </d>"
  }]
}
```

## 四、双侧共同规则（同一张表，两侧各跑一遍）

| # | 规则 | 级别 | 为什么 |
|---|---|---|---|
| 1 | `shots` 非空 | **fail** | 没有镜头，渲染无从下手 |
| 2 | 镜头 `id` 为正整数、不重复 | **fail** | id 同时是产物文件名，重复＝后渲覆盖前渲 |
| 3 | `scene` 引用存在于 `scenes[].id` | **fail** | 悬空＝该镜拿不到环境参考图 |
| 4 | `characters` 引用存在于 `characters[].id` | **fail** | 悬空＝定妆照挂空 → 跨镜换脸 |
| 5 | `duration ∈ [4, 10]` 秒 | **fail** | H3 帧网格与单镜成本的合法区间 |
| 6 | `h3_prompt` 非空 | **fail** | 没有可提交的提示词 |
| 7 | 角色/场景 `id` 非空 | **fail** | 引用体系的地基 |
| 8 | **台词+旁白时长 ≤ 镜头时长** | warn→自动抬 | 4.5 字/秒 + 0.3 收尾；抬到 10 秒仍不够 → **如实报"建议拆镜"**（这是"配音不完整"的病根） |
| 9 | 台词段带 `<d>[Chinese]` 标记 | 自动补 | 标记丢了 H3 会用任意语言说话（成片出现听不懂的鸟语） |
| 10 | `mode ∈ {ref2va, t2va, ""}` | warn | 未知值平台按空值推断 |
| 11 | `shot_size` 在中文白名单内（Contains 判） | warn | 不在族里 → 参考图拼合按"保留其它角度"处理 |
| 12 | 镜头号 1..N 连续 | warn | 断号会让产物清单看起来像丢镜 |
| 13 | `style` 非空、角色/场景有 `image_prompt` | warn | 缺风格句画风会漂；缺提示词 → 参考图只能现编 |
| 14 | 角色/场景 `name` 非空、台词有说话人 | warn | 提示词与字幕可读性 |

**级别语义**：fail ＝ 平台**拒收**并逐条列出"哪一条、在哪"（`400` + `fails` 数组）；
warn ＝ 收下但**如实回显**（响应 `warns` + 运行日志），不静默。

**常量同源**（4 / 10 秒、4.5 字/秒、0.3 收尾）：平台侧在 `internal/project/plan_contract.go` 与
`internal/director/dialogue.go` 各有一份，由 `plan_contract_ext_test.go` 断言相等 ——
谁改了一边，测试立刻红。技能侧同值写在 `scripts/manju_plan.py`，并由两侧各自的击穿用例钉住。

## 五、两侧入口

**技能端**（产出 + 自检，产出前不许交违规包）：

```powershell
$py = 'D:\Ai\ComfyUI\standalone-env\python.exe'
$mp = "$HOME\.dsh\skills\manju-novel\scripts\manju_plan.py"
& $py $mp build --project 'D:\Ai\小说\<书名>' --episodes all --out <包目录>   # 小说 → 项目包（全集/选集）
& $py $mp check --series <包目录>                                          # 契约自检（同规则表）
& $py $mp emit  --series <包目录> --manjux-data 'D:\Ai\Datas\ManJuX\data'   # 落到平台数据目录
& $py $mp bridge --project 'D:\Ai\小说\<书名>' --out <包目录> --manjux-data 'D:\Ai\Datas\ManJuX\data'
                                                                            # 一条命令：build(全集)→check→emit
```

`--episodes all|1|1-5|1,3,7`（默认全集）；`--llm` 让模型只决定"怎么切/景别/运镜/谁说的"
（每镜必须带原文逐字片段、脚本回原文定位，**覆盖率 <85% 自动回退机械基线**，文字与时长永不交模型）；
角色/场景 id 落书级 `_pool.json`，**默认不重建**（平台按 id/名字复用 assets，换 id 就是换脸）。

**平台端**（解析 + 守门 + 重扫）：

```
POST /api/projects/{id}/import-plan   body {"plan": {...}}    ← 校验 + 后处理 + 存盘
POST /api/projects/import-package     body {"path": "..."}    ← 技能端整包入库（单集包或系列根）
POST /api/projects/rescan                                     ← 手工重扫（一般用不上）
GET  /api/projects                                            ← **读路径自带重扫**
```

**`GET /api/projects` 自己重扫**（2026-09-26 收尾）：界面从来没有"重扫"这个动作，
若只在启动时扫一次盘，技能端 `emit` 完用户还是得关掉应用再打开 —— 链路最后一环就断在
"界面看不见刚产出的集"。所以列表读路径每次顺手 `Store.Rescan()`：已装载的项目直接跳过
（不重读元信息），成本是几次 `readdir`；**语义仍是只新增不删除**。
`import-package` 是包还在别处时由平台自己拷进来（技能端不必知道平台的数据目录布局），
逐包校验后**整批入库，全有或全无** —— 任一项不过契约校验就一个字段都不落盘：
半个系列混进 Store 比导入失败难查得多（作者分不清哪些集是新的）。`.mp4` 等体积产物一律不复制。

**系列根按 `series.json` 对账**（同上）：技能端在 `series.json` 里声明这本书有哪几集、
各是哪个目录。声明了 N 集却只找到 M 个包（`M<N`，拷贝中断/只拷了一半）= **拒收**并点名缺哪几集，
给的办法是"只想导一部分就把 `series.json` 移开"。平台**不拿它当数据源**（数据源永远是各集自己的
`plan.json`），只用它对账：半套系列静默入库，与"半导入状态"是同一类坑，只是发现得更晚
（渲染到第 20 集才发现缺）。没有 `series.json` 的目录 = 逐包导入，照旧。

`importPlan` 对**导进来的包**做与 `PhaseScript` **同等的后处理**
（`director.FitDialogueDurations` + `pipeline.EnsureChineseDialogue` + `DialogueOverflow` 警告），
所以「导进来的」与「平台自己生成的」在渲染眼里完全等价 —— 这是分工能成立的前提。

## 六、同步纪律（双侧共组怎么维护）

1. **改规则 = 改版本号 + 两侧同提交**。`PlanContractVersion`（平台）与 `CONTRACT_VERSION`（技能）必须同号；
   版本号变了就在本文档追加一节说明。
2. **每侧都跑同一张表**：技能端 `manju_plan.py check`、平台端 `importPlan` 守门。
   任何一侧放宽，另一侧就会把违规包放过去 —— 所以两侧都要有**击穿用例**。
3. **击穿用例是硬要求**（与技能侧 `qa_selftest.py` 同一条纪律）：
   - 平台侧：`internal/project/plan_contract_test.go`（每条规则一个反例）+ `internal/server/import_plan_test.go`
     （入口：校验拒收、后处理等价、包导入全有或全无、重扫）；
   - 技能侧：`scripts/manju_plan_selftest.py`（23 条，含池子稳定性与 LLM 覆盖率守卫）。
   **门必须证明它会拦，也要证明它不乱拦**（合规样本零 issue）。
4. **文案不许骗人**：拒收时响应体给出 `fails` 明细；收下时把 `warns` 与"调整了哪些镜的时长"一并回显 ——
   "静默通过和撒谎只差一步"。

## 七、版本历史

- **v1.1（2026-09-26，同日补齐落地环节）**：契约本身没动，补的是"脚本怎么进平台、怎么一次做全集、界面怎么看见"：
  技能端新增全集/选集批处理（`--episodes`/`--all`/`--chapters-per-episode`）、书级 `_pool.json`
  （跨集 id 稳定，`--rebuild-pool` 才改）、`--llm` 精修（覆盖率守卫，<85% 回退基线）、
  `bridge` 一条命令（build→check→emit，任一集 fail 整批不投放）、`emit` 投放前守门；
  平台端新增 `POST /api/projects/import-package`（单集包/系列根，**全有或全无**），
  并让 **`GET /api/projects` 读路径自带重扫** —— 界面没有"重扫"动作，这一环不接上，
  技能端产出后用户还是得重启应用才看得见。
- **v1（2026-09-26）**：契约建立。技能端产出 `plan.json` + 项目包；平台端 `importPlan` 从
  "只查有没有 shots 数组"升级为**按规则表守门 + 与 script 阶段同等的后处理**；
  新增 `POST /api/projects/rescan`（技能端直接写盘的项目不用重启就能被平台看见）；
  新增 `project.ValidatePlan` 与两侧击穿用例；常量同源由外部测试包断言。
