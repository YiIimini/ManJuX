# 自动 Q 版接回「以定妆照为参考图派生」+ 画幅收口（2026-10-10）

用户原话：

> Q 版卡有对应的角色直接可以图生图为 Q 版形象能简单一点吗？

**能 —— 而且平台早该这样。** 派生链路 2026-09-28 就按同一条口径建好了，**唯独自动那条支线漏接了**。
本轮把接线接上，顺手把两处「写死 1024×1024 方图」的口径收口（Q 版图会被挂进参考图位）。

---

## 一、取证（先看清哪条路走了岔）

| 出图路径 | 改动前 | 证据 |
|---|---|---|
| **方案里的 Q 版卡**（`char_xxx_q`「灵影小自己」） | ✅ **已经派生** | 走 `genAssetImage → genSheetImage`，`sheetderive.go` 的 `ChibiDeriveClause` / `ChibiDeriveDenoise = 0.75` / `qc.IdentityJudge` 闭环都是为它写的（2026-09-28 用户口径「Q 版直接使用对应角色定妆照图片生图片逻辑才对」） |
| **自动支线**（`char:<本体id>_chibi`） | ❌ **纯文生图** | `stages_assets.go` 直接 `comfyGen.GenerateImage(chibiPrompt, …, 1024, 1024, out)` —— 没有参考图 ⇒ 把长相重新描述一遍 ⇒ 必然「像但不完全像」的第二张脸；也正因如此 Q 版提示词才要背整段长相 |

换句话说：**用户指出的这条"更简单"的路，平台里已经写好并在方案卡那条路上跑了，只是自动支线自己另立了一次文生图**。
这正是本仓反复栽的「同一件事两处实现」：改一处忘一处。

## 二、修法（最小接线 + 两处口径收口）

**① 自动支线走唯一出口**（`internal/pipeline/stages_assets.go`）：
`comfyGen.GenerateImage(...)` → `c.genSheetImage(ctx, comfyGen, sheetJob{kind:"characters", id: ch.ID+"_chibi",
name: ch.Name+" · Q版", desc: ch.Description, prompt: chibiPrompt, ek: KindChibi, w: cw, h: chh, seed: seed})`
⇒ 走 `deriveVariantSheet`：编辑链（Qwen-Image-Edit 2.1，`Qwen 的参考图只能走编辑图`）优先、图生图兜底、
两条都不行才**如实播报**退回文生图；出图后 `qc.IdentityJudge` 拿定妆照判一次身份，不过就换种子重出一轮。
落盘路径与资产键**没变**（`assets/characters/characters_char_<id>_chibi.png`，同一条 `SanitizeForCache`）。

**② 画幅收口**：Q 版图会被挂进内心镜的**参考图位**（`refs.go` 的 `character_chibi`），
而「参考图 = 成片画幅」是既有设计（`asset_size_test.go` 顶着"比例不对 ⇒ 构图漂移从第一帧就埋下"）。
原先**两处**都写死 1024×1024 方图：
- 自动支线（本轮改）：`cw, chh := assetImageSize(proj, "characters")`；
- 单资产「重新生成」（`coordinator.go`）：删掉 `if isChibi { w, h = 1024, 1024 }` 那段特例。

那条注释原本写着"两边同一口径" —— 是真的，但**那是同一个错**。

## 四、生效范围

- **新建/重跑资产阶段**：自动 Q 版即走派生（第一次出图就需要本体定妆照已就绪 —— 自动支线本来就排在角色循环之后）。
- **存量项目**：已经生成过的方图 Q 版**不会自动变**；在资产库/抽屉里点「重新生成」即走新口径
  （随机种子 + 从本体定妆照派生 + 成片画幅）。
- **没有参考图时**（主卡缺图 / 引擎不支持编辑与图生图）：**如实播报**后退回文生图，不静默。
- Q 版仍**不进** `refs.go` 的角色参考图集合（它是 `character_chibi` 那一档，只在内心镜用），
  所以这次改的是"它的画幅与本体同源"，不是它的挂载口径。

## 五、如实说的边界

- **本轮没跑真机出图 A/B**（要 ComfyUI 冷启动 + 逐张出图）：验证是**门 + 反向验证 + 接线取证**，
  不等于"派生出来的 Q 版一定比文生图好看"。要验的话一条命令：
  `go run ./cmd/imagecheck -prompt-file <探针写出的 Q 版提示词> -w 768 -h 1344`（对照旧文生图那张）。
- 编辑链是否就绪取决于本机权重（`EditReady` 会点名缺哪一项）；缺了就按图生图跑，再不行才文生图 + 播报。
- 自动 Q 版仍受**方案里已有 Q 版卡就跳过**（2026-09-25 用户口径：避免同一形象两份）与
  锚表「Q版形象：无」的限制，本轮没动这两条判据。

## 六、附带修掉一处真机卡死：孙进程握着 stdout 管道（`WaitDelay`）

**真机咬到**（就在本轮跑八门自检时）：`internal/pipeline` 整包的 `go test` **卡到 600s / 900s**，
栈停在 `os/exec` 的 `io.copyBuffer`，被卡住的正是逐镜语音核对那条链
（`voice_check.go` → `qc/speech.go` → `asr/asr.go` 的 `cmd.CombinedOutput()`）。

**根因**（Go 的经典坑，不是这台机器的毛病）：工具链是 `asr.cmd`(**cmd.exe**) → `python.exe`
（python 可能再拉起解码器）。ctx 到点或进程退出时，被清算的只是 **cmd.exe**，
**孙进程还握着 stdout 管道** ⇒ `CombinedOutput` / `Wait` 会一直等"管道读完"。
同一形态在装配引擎那条链上更危险：`python` → `ffmpeg`，用户点一次「停止」就可能把 UI 线程吊住。

**修法（一处收口）**：`sysexec.Hide` 给每个子进程设 `cmd.WaitDelay = 3s`
（Go 1.20+；只在"进程已退出 / ctx 已取消而管道仍被握着"时生效，正常路径完全不受影响）。
调用方**认得** `exec.ErrWaitDelay`：

- `asr.Transcribe`：结果本来就从 **文件** 读（`<media>.asr.txt`），所以"文件读得回来"才是判据 ⇒
  收到 `ErrWaitDelay` 但结果解析成功 ⇒ **算跑成**；文件读不回来或退出码真非零 ⇒ 照样如实报错。
- `compose/engine.go`：判成功本来就是"引擎报告了 `ASM-DONE`"（紧接着读时间轴文件）⇒
  `ErrWaitDelay` 不再被当成拼接失败。

**门**（`internal/sysexec/waitdelay_test.go` + `internal/asr/transcribe_test.go`）：

① `TestHideSetsWaitDelay` —— 判据直接喂 **Hide 本体**（`cmd.WaitDelay > 0`）；
② `TestWaitDoesNotHangWhenGrandchildHoldsPipe` —— **行为级**：临时 `.cmd` 里 `start "" /b` 起一个
   活 30 秒的**孙进程**（继承 stdout 管道）后立刻退出 ⇒ `CombinedOutput` 必须 ≤ 15 秒返回
   （实测 **3.01s** 返回；去掉上限会等到 30s）；
③ `TestTranscribeSurvivesGrandchildHoldingPipe` —— 照 **ASR 真实形态**：假工具先写结果文件、
   再起孙进程、然后退出 ⇒ `Transcribe` 必须 ≤ 20 秒返回**并解析出段落**（实测 **3.02s**）。

**反向验证 3/3 全红**（`scratch/reverse_verify_waitdelay.ps1`：把 `cmd.WaitDelay = waitDelay` 改成 0
⇒ 上面三道门全红）。

**如实说**：第一次卡死是**瞬时**的（同一台机器、同一份代码，随后同样一条用例 73 秒通过）——
我没有把"当时为什么被触发"钉死；但"孙进程握管道就能把链路吊死"这条机制是**确定**的（门与反向验证
都建在真实子进程计时上），而且它本来就迟早会在生产里咬人（质检逐镜跑 ASR，或用户点「停止」）。
