1. **G15 / P0-4（"配置卫生：`grade` 从 `auto` 改成真实档位名"）不成立。**

### 1.8 常见运镜习惯

| 项目 | 值 | 来源 |
|---|---|---|
| 景别 | **近景 + 中景为主**，避免长时间特写 | 【检索】万众编剧网 |
| 转场 | 淡入淡出、推拉；避免花哨转场 | 【检索】万众编剧网 |
| 分镜节奏 | 每 10–15 秒一个小冲突，30 秒一个反转 | 【检索】万众编剧网（这是剧作节奏，不是画质参数） |
| 与压缩相关的运镜纪律 | 一个镜头只用**一种**摄影机运动；镜头不动能让至少一个轴可预测；避免摇镜/手持抖动/背景闪烁 | 【检索】Versely |

**关键结论**：H3 生成时若镜头行为描述不清，模型会用"默认漂移"填满——**漂移是编码器要为之付码率、却没有叙事回报的运动**（【检索】Versely 原话意译）。这对漫剧的 prompt 写法是一条可以直接用的纪律。

三条容易被忽略但确定的事实：

1. **色彩 transfer 是 `iec61966-2-1`（即 sRGB），不是 bt709**。VUI 组合是 `bt709 / bt709 / sRGB`——一个非标准混搭。而仓库的 `x264Transfer` 映射表里**有** `iec61966-2-1`【源码 `internal/compose/color.go:205`】，意味着这个标记会被**原样写进成片**。
2. **音源只有 32 kHz**。H3 的音频 VAE 产物上限就在这里，compose 后面 resample 到 48 kHz 只是"填格子"，补不回 16 kHz 以上的频带。
3. **每个镜头文件里塞着整份 ComfyUI 工作流 JSON**（`prompt` 标签）。体积不大但属于导出卫生问题。

## 4. 可执行的配置方案（三层）

> 每项都标 **改法**（配置 / 代码）、**具体参数**、**代价**、**证据等级**。

### 4.1 ① 渲染层

#### 4.1.1 加速档与步数 —— **收益最高、成本可控**

**A 档（推荐，改配置即可）**：`params.render.accel = "refine"`

- 效果：**不挂任何蒸馏 LoRA**，`accelSteps` 强制步数 ≥20（`engine.go:818-824`）；`stages_render.go:38` 的"turbo 时钳到 8 步"对 refine **不生效**，所以 20 步能真正跑满。
- 依据：源码注释把三档语义写得很清楚——`turbo = 官方 Turbo 4step（最快，人物偏糊）`、`quality = Kijai Acc-8Step（人物质感/清晰度显著优于 Turbo，慢约 20%）`、`refine = 不挂任何蒸馏 LoRA，按完整步数采样`（`engine.go:776-789`）。
- **代价**：采样步数 8 → 20，采样阶段时间约 **2.5×**（【推测】，按步数线性外推；蒸馏 LoRA 不改变单步成本量级，故线性外推是合理的一阶近似。**要确认必须用单镜计时实测一次**）。其余（VAE 解码、编码）耗时不变。
- 附注：这会让 `renderFingerprint` 追加 `accelrefine` 标记（`stages_render.go:460-463`）→ **存量镜头会被判定失效并重渲**，这是有意的。

**B 档（更省时间，改配置即可）**：保持 turbo，但把 `steps` 改成 **4**

- 效果：与 4 步蒸馏 LoRA 的锚定值对齐，采样时间减半。
- 依据：官方 turbo LoRA 名为 `..._turbo_4step_...`（【实测】文件名）；源码注释称其为"官方 Turbo 4step"。
- 代价：几乎零成本。观感应与当前 8 步基本一致（【推测】：蒸馏权重在 4 步处是设计工作点）。

**关于 `quality` 档：不要动。** 本机没有任何非量化 H3 底模，选它只会静默回退 Turbo（§2.7）。要真正用上 Acc-8Step 必须引入非量化底模（fp16/fp8_scaled，量级 40GB 且 24GB 显存需 offload，速度骤降）——**不建议**。

**`express` 档**：官方 Turbo + int8 VAE，更糊，仅适合抽卡预览，**不要用于交付**。

#### 4.1.2 底模与精度

- **不建议换底模**。理由：本机无非量化 H3 底模；24GB 显存跑 fp16 需 offload。
- **有一件事值得 A/B**【推测，需实测】：`ref2va` 这条当前用的是 **`Minimax-h3_Singularity_ref2va_Pruned_v1.3_int8`**，而同目录里还躺着官方的 **`MiniMax_H3_ref2va_pruned_int8_convrot`**（fl2va 那条用的正是官方 convrot 版）。两条 ref2va 底模并存、且 ref2va 用的不是官方那个——建议用同一 prompt+seed 各渲一镜做 A/B，这是零成本的验证（只花两次渲染时间）。
- `w4a8` 底模（10.96GB）更低比特，**画质通常更低**（【推测】），不建议用。

#### 4.1.3 采样参数

`res_multistep` / `simple` / `SigmaShift(12,3)` 都是官方默认。**不建议动**——没有可依据的更好取值，改了就要重建整条画质基线。

#### 4.1.4 分辨率与放大策略：**是否值得上 2K 再缩回？**

先明确三条**已确认的硬边界**：

1. H3 本地渲染上限：短边 ≤768（`config.go:102`）。
2. 云端 2K 再生成：源必须是 **H3 768P 产物（短边正好 768、长边 ≤1344、必须带音轨）**（`h3api/regen.go:104-113`）；而 **`settings.json` 里 `minimax.api_key` 是空的** → 当前**不可用**（【实测】配置文件）。
3. 本地 2× 放大链**已经存在**：`esrgan`（`4x-UltraSharp`）与 `ltx`（`ltx-2-spatial-upscaler-x2-1.0` + `LTX2_video_vae_bf16`）两条，且承诺**精确 2×**（`upscaleTargetFactor`，`upscalegraph.go:71`），即 768×1344 → **1536×2688**。权重【实测】都在本机。

**结论：值得试，但形态是「1536×2688 母版 → 缩到 1080×1920 交付」，不是「768 → 直接放大到 1080」。**

- 理由（部分【实测】、部分是【推测】）：从 768 直接 lanczos 到 1080 是 **1.41× 插值放大，不产生任何细节**（【实测】它确实生成了 5.04 Mbps 的码流，但那是插值出来的平滑像素）；而从 1536×2688 缩到 1080 至少有 **1.42× 的超采样**，边缘会更干净（【推测】，必须抽帧 A/B 验证，见 §6）。
- **代价**：每镜多一次「解码 → 空间放大 → 编码」。LTX 路线按 `tile_size=512, overlap=64, temporal_size=64, temporal_overlap=8` 跑（`upscalegraph.go:144-155`），1536×2688 的显存压力较大（【推测】，需实跑一次看有没有 OOM / 是否触发 ComfyUI 的 tiled fallback）。
- **一条值得单独试的路**【推测，未验证】：本机有 **`minimax_h3_latent_upscaler_3d_conv_v1_bf16.safetensors`**——从命名看是 **H3 自己的** 3D 卷积隐空间放大器。但 ManJuX 当前只实现了 `ltx`/`esrgan` 两条链，`ltx` 走的是 `LTXVLatentUpsampler` 节点（`upscalegraph.go:148-151`），**没有接线到 H3 那个权重**。理论上 H3 原生放大器比通用 LTX 更贴 H3 的隐空间分布（【推测】）。要试需要先确认 ComfyUI 里对应的节点名——**未验证，不要直接当成可用方案**。

**如果 2K 路线太贵，退一档的最优解**：交付 1080×1920 用 `xbr` 或 `lanczos` 放大（见 §4.3.4），成本几乎为零，至少把"放大算法"这件事从平台手里拿回来。

### 4.2 ② 后处理层

#### 4.2.1 调色档：**颗粒是本方案第一优先级**（改配置即可）

**建议**：

| 场景 | 档位 | 理由 |
|---|---|---|
| **交付版** | `soft`（无颗粒、无暗角，只抬对比+轻锐化 0.5）或 `film` 但**把 `noise` 降到 0–3** | 【实测】颗粒把码率从 2.79 → 6.99 Mbps（2.5×）；【检索】平台二次编码**第一个牺牲的就是颗粒** |
| 情绪戏/夜戏 | `heavy` 仅用在**局部镜头**，且要有意识接受它的码率代价（颗粒 10） | 【源码】heavy = film + 颗粒 10 + 2px 色差 |

**代价核算（实测）**：去掉颗粒省 **4.2 Mbps / 63% 码率**；观感上损失的是"胶片质感"，但这份质感在抖音/红果链路上**大概率不会存活到观众眼前**（【检索】Versely 明确："a heavy grain pass as the last step before upload is a pass the audience will never see, except as mush"）。

若要保留一点质感，**把质感做在大形状上**：film 档的 `contrast=1.12 / saturation=0.94 / gamma=0.96` 与 `colorbalance` 冷阴影暖高光**都不吃多少码率**（【实测】去掉 noise 后整条链是 2.79 Mbps，与纯 crf18 的 2.01 Mbps 同量级），这部分可以保留。

**配置卫生（顺手修）**：`project.json` 现在写的是 `"auto"`——一个**不存在的档位名**，靠 `NormalizeGrade` 的兜底静默跑成 film（`grade.go:64-69`）。建议显式写成 `"soft"` / `"film"` / `"off"`，别让配置文件撒谎。

#### 4.2.2 锐化：**挪位置，而不是加量**

- 现状：`unsharp=5:5:0.8` 在 **768 原生**上做（film 档，`grade.go:36`）。
- 建议：锐化应该在**放大到交付分辨率之后**做一次，量取 **0.4–0.6**（5×5 luma，chroma 0）。
- 理由（【推测】为主）：在 768 上锐化会把 H3 本就偏软的边缘放大成光晕（overshoot），这些高频又被平台转码削掉；在放大后锐化，作用在真正的交付像素上。**必须抽帧 A/B 验证**，不要盲改。
- **代价**：需要在 compose 的滤镜链里调整顺序（调色在 scale 之后、字幕之前），属**代码改动**。

#### 4.2.3 颗粒 / 降噪 / 时域稳定

- **颗粒**：见 4.2.1，**减**。
- **音频降噪**：当前 `denoise=true` → `highpass=f=70,afftdn=nr=12:nf=-30`（`compose.go:533`）。**注意这是音频链，不是画面降噪**，别被参数名误导。建议**保留**，但要戴耳机确认人声没出现"水下感/发闷"（`nr=12` 属中等偏激进，【推测】）。
- **画面时域降噪：当前完全没有，且这是收益明确的一块**【推测，需 A/B】。H3 类视频模型常见 texture boil / 背景闪烁，【检索】Versely 明确指出"时域缺陷在平台二次编码后**会变成块状闪烁**（blocky shimmer）"，并建议"在生成侧解决，别指望 feed 帮你抹平"。本地可行的轻度方案：`hqdn3d`（如 `hqdn3d=1.5:1.5:6:6`）或 `atadenoise`，加在调色之前。
  - **代价**：可能把细节糊掉（这正是锐化要补回来的地方），且滤镜耗时增加。**必须先抽帧对比再决定**。
  - 优先在**生成侧**解决：把"镜头运动描述得更明确"（避免默认漂移）、避免会让模型发狂的高频纹理背景（【检索】Versely 的"clean plates"建议）。

#### 4.2.4 帧率处理：**不补帧**

- 24fps 落在平台可接受区间（23–60fps，【检索】），整片统一 24fps 已经在做（`compose.go:125`，【实测】两个镜头都是恒定 24/1）。
- 补帧到 30/60 的代价：需要额外节点（RIFE/FILM），易出伪影；且【检索】Versely 指出"在固定交付码率下，更多帧通常意味着每帧更少的位数"——**这是净亏**。
- **不建议**。（唯一改动的理由：如果将来确认红果硬性要求 ≥25fps——目前**没有取到**这样的官方依据。）

### 4.3 ③ 编码封装层

#### 4.3.1 当前实际参数（先复述清楚，再谈改法）【源码】

见 §2.5。一句话版本：**全链 `libx264 -preset medium -crf 18 -pix_fmt yuv420p`；音 `aac 192k -ar 48000 -ac 2`；终混带 `-movflags +faststart`；色彩标记用 `-x264-params` 写入。**

#### 4.3.2 CRF / preset / tune / profile

| 项 | 建议 | 实测代价 | 证据 |
|---|---|---|---|
| `-crf` | 18 → **16**（若走 1080 交付，18 已能到 5 Mbps，可保持 18；若坚持 768 交付则必须降 CRF 补码率） | crf14 = 2.90 Mbps(+44%)、crf12 = 3.68 Mbps(+83%)（均@768 源） | 【实测】 |
| `-preset` | medium → **slow** | 1080p@crf20：medium 3.79 Mbps / 1.5s → slow 3.60 Mbps / 2.1s（**省 5% 码率，慢 40%**，绝对耗时仍可忽略） | 【实测】 |
| `-tune` | 试 **`animation`**（内容为 2D 漫剧，x264 有专门的 animation tune） | **未实测**，需跑一遍确认码率/观感变化 | 【推测】 |
| `-profile:v/-level` | **不用写**（x264 默认按输入自动算，见文首「执行状态」第 2 条） | 零 | 【实测】源片标注的 `High@L3.2` 就是自动算出来的 |
| 硬切路的 `-c:v copy` | **保持**（这是仓库已经做对的一处：不为"什么都没做"再压一代） | — | 【源码】`compose.go:284-292` |

#### 4.3.3 色彩元数据

- **现状【实测】**：单镜 VUI = `range=tv, space=bt709, primaries=bt709, transfer=iec61966-2-1`。`color.go` 的 `marked()` 只要求"矩阵或原色有值"即算已标记（`color.go:47`），所以这一组会被**原样透传**进成片；`x264Transfer` 表里确实列了 `iec61966-2-1`（`color.go:205`）。
- **目标**：网络交付缺省 **Rec.709**（【检索】ClipSkills）。
- **建议**：在**终混**那一步把 transfer 归一成 `bt709`（**只改标记，不做像素转换**）。
- **风险与纪律**：这与 `color.go` 的核心纪律"**绝不强改已标记的源**"（文件头注释 15-24 行）是**有意的例外**，因为这里的 `iec61966-2-1` 不是"素材本来的口径"，而是 ComfyUI 写出来的一个非标准缺省。sRGB 与 BT.709 的 OETF 不同，改标记会让播放器换一套曲线解码 → **必须抽帧目视确认没有整体明暗偏移**。
- **优先级**：P1，**单独上、单独验**，不要和其他改动混在一起。
- **另一条**：`color.go` 里还有"各镜标记不一致就不统一改写、只播报"的分支（`color.go:126`）。多镜头项目要先看日志里有没有这条告警。

#### 4.3.4 交付放大（G1 的落地方式）—— **需要改代码** ✅ 已落地（2026-09-27，方案 2）

**做不到"只改配置"**，原因见 §3 末尾：`render.width/height` 同时驱动渲染与交付。

可行的改法（三选一，从省事到讲究）：

1. **在终混滤镜链最前面加一步 scale**（`scale=1080:1920:flags=lanczos` 或 `flags=xbr`）。改动最小，代价：零额外编码代次（本来就要重编一次）。
2. **在 compose 里新增一个"交付分辨率"参数**，与 `render.width/height` 解耦（更干净，但要动参数契约与前端）。
3. **走 §4.1.4 的 2K 母版路线**，然后缩到 1080（成本最高，收益也最高）。

**实测代价**（对 7.29s 片段）：1080×1920 crf18 → 5.04 Mbps / 4.49 MB / 编码 1.6s。相对 768×1344 是**文件 ×2.5、耗时 +0.9 秒**。

**不要上 4K**：【检索】手机 feed 不会保留 4K 的像素（Versely 明确"4K 会花掉你的时间和额度，观众拿到的还是 1080p 级的编码"；ClipSkills 也把抖音列为 9:16 / 1080×1920）。

| 中间轨 | 拼接阶段走 FLAC 无损【源码】 | 保持（已做对） | 【源码】 |

## 5. 优先级排序

### P0 —— 收益最大 + 成本最低（建议立刻做）

| 序 | 动作 | 改法 | 收益 | 代价 | 证据 |
|---|---|---|---|---|---|
| **P0-1** | **交付版去掉/大减颗粒**（film → soft，或 `noise` 6→0~3） | 改配置 `assemble.grade` | 码率 **2.5×↓**（6.99→2.79 Mbps）；且颗粒本来就会被平台吃掉 | 零 | 【实测】+【检索】 |
| **P0-2** | **显式设置加速档**：要么 `accel="refine"`（画质优先），要么 `steps=4`（时间优先） | 改配置 | refine：换掉蒸馏权重、拿到完整采样；steps=4：采样时间减半且观感不变 | refine ≈ 2.5× 采样时间（【推测】）；steps=4 ≈ 0 | 【源码】 |
| **P0-3** | **字幕 MarginV 8% → 12–15%** | 改配置/改 `compose.go:940` 的系数 | 避开平台底部 UI 遮挡区 | 零 | 【检索】+【源码】 |
| **P0-4** | **修配置卫生**：`grade` 从 `"auto"` 改成真实档位名 | 改配置 | 消除"配置文件撒谎、系统静默兜底" | 零 | 【源码】 |

> 注：P0-1 与 P0-2 是**互斥权衡**——refine 加时间、去颗粒减码率，两者一起上是"用时间换画质"，方向一致，可以同时上。

### P1 —— 收益明确，但要验证 / 要改代码

| 序 | 动作 | 为什么排在 P1 |
|---|---|---|
| **P1-1** | **交付分辨率解耦并升到 1080×1920**（§4.3.4） | 收益最大的一条（G1），但**必须改代码**，且要选实现方案 |
| **P1-2** | 编码参数：`preset slow` + `crf 16` + 试 `tune animation` | 实测代价清楚、收益明确，但要改源码且需回归测试 |
| **P1-3** | 锐化从 768 挪到放大之后（§4.2.2） | 需要调整滤镜链顺序，且必须抽帧验证 |
| **P1-4** | 色彩 transfer 归一 bt709（§4.3.3） | 触及 `color.go` 的核心纪律，必须单独上、单独验 |
| **P1-5** | 画面时域降噪试验（§4.2.3） | 收益取决于 H3 当前 boil 的严重程度，**要先抽帧看** |
| **P1-6** | 2K 母版路线（1536×2688 → 缩 1080） | 收益最高但成本最高（显存/耗时未知），**建议先做单镜 A/B 再决定** |
| **P1-7** | H3 原生 latent upscaler 接线验证（§4.1.4） | 与 P1-6 相关，属探索项 |
| **P1-8** | ref2va 底模 A/B（Singularity v1.3 int8 vs 官方 convrot int8） | 零成本（只花两次渲染），**性价比很高，可以提到 P0 后面立刻做** |

### P2 —— 锦上添花

- 显式写 `-profile:v high -level 4.0`（提高播放器兼容性）
- 清理导出文件里的 ComfyUI `prompt` 元数据（§4.3.7）
- 台词色从金色改成白色（贴近大盘观感，纯风格选择）
- 把"颗粒质感"改为在 prompt/生成侧解决（而不是后处理叠噪点）

### 不建议做

| 项 | 理由 |
|---|---|
| 上 4K 交付 | 【检索】手机 feed 不保留 4K；文件/耗时成倍 |
| 换非量化 H3 底模 | 本机没有；24GB 显存跑 fp16 需 offload，速度骤降。收益【未取到】证据 |
| 用 `quality` 档 | 本机**必然静默回退 Turbo**（量化底模），是空操作 |
| 补帧到 30/60fps | 易出伪影；固定码率下每帧位数更少（【检索】）；不改画质只改流畅度 |
| 改 `res_multistep` / `simple` / `SigmaShift(12,3)` | 官方默认，无据可依，改了要重建基线 |
| 把已标记为非 bt709 的源片强改 bt709 | `color.go` 的既有纪律（会让整片偏色） |
| 继续在 768 原生上叠加锐化/颗粒找"电影感" | 实测：颗粒 2.5× 码率、锐化吃高频；两者都会被平台二次编码削弱 |
| 提高 `loudness` 去追"平台目标响度" | 平台目标值【未取到】，无依据 |

```powershell
$VF = "scale=768:1344:force_original_aspect_ratio=decrease,pad=768:1344:(ow-iw)/2:(oh-ih)/2,fps=24,setsar=1"

```

**② 颗粒的码率代价**

```powershell
$FILM = "eq=contrast=1.12:saturation=0.94:gamma=0.96,colorbalance=rs=-0.04:gs=-0.01:bs=0.06:rm=0.02:bm=-0.02:rh=0.04:gh=0.01:bh=-0.05,unsharp=5:5:0.8:5:5:0.0,vignette=PI/4.5,noise=alls=6:allf=t+u"
& "$ff\ffmpeg.exe" -v error -y -i $src -vf "$VF,$FILM" -an -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p "$w\graded.mp4"
& "$ff\ffprobe.exe" -v error -select_streams v:0 -show_entries stream=bit_rate -of csv=p=0 "$w\graded.mp4"
# 去掉 noise= 那一段再跑一次做对比
```

**③ 交付 1080 的代价**

```powershell
& "$ff\ffmpeg.exe" -v error -y -i $src -vf "scale=1080:1920:flags=lanczos,fps=24,setsar=1" -an -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p "$w\hd.mp4"
& "$ff\ffprobe.exe" -v error -select_streams v:0 -show_entries stream=bit_rate -of csv=p=0 "$w\hd.mp4"
```

**⑤ 整镜计时（P0-2 的必要前置）**：refine 档（≥20 步）相对当前 8 步的真实耗时倍数**必须实测**——本文给的是按步数线性外推的【推测】值（≈2.5×），不是量出来的。

## 9. 如果只做三件事

> **落地进度（2026-09-27）**：第 1 件（去颗粒）与第 3 件（字幕安全区）已做；
> 第 4 件（交付升 1080×1920）也已做（解耦成 `assemble.deliver_width/height`，默认按画幅自动）；
> **只有第 2 件（`accel=refine` + 步数）没做** —— 它需要一次真机单镜计时，而那要先有能渲的项目。
> 明细见文首「执行状态」。

1. **`assemble.grade` 改成 `soft`（去掉 `noise=6`）** —— 实测省 2.5× 码率，零成本，且颗粒在平台侧本来就会消失。
2. **`render.accel` 显式设成 `refine`，步数给到 24–28** —— 换掉 4 步蒸馏权重、拿到完整采样；这是本机唯一能实质提升画质基线的渲染层开关。先实测一次单镜耗时再全量上。
3. **字幕 `MarginV` 从 8% 提到 12–15%** —— 零成本避开平台底部 UI 区。

第 4 件（**交付分辨率升到 1080×1920**）收益比上面三件加起来还大，但它**必须改代码**——`render.width/height` 现在同时驱动 H3 渲染和成片交付，动它会把 H3 推到它不支持的 1080×1920 上去。这条要单独立项。
