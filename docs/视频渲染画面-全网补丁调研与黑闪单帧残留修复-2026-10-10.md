## 0. 一句话结论

1. **上游没有"专门修画面"的补丁可捡**：ComfyUI 从我们在用的 `v0.39.1` 到最新 `v0.39.2` 只有 6 个 commit
   （4 个 Partner Nodes + 模板版本 + 版本号），**与本地 H3 出图路径一个字都不沾**；官方 H3 权重自 **2026-09-29**
   没再动过。社区那一堆"画面增强/续接/放大"插件**全部要装第三方节点 + 两遍采样**，而且**没有一个**为
   "int8 剪枝底模 + Turbo LoRA + 8 步"这条链做过验收 ⇒ 按本仓纪律**不给背书、不接**（判据与成本见 §4）。
2. **反而在真机上咬出我们自己那条"剪黑闪"补丁的一个真缺陷**：黑段 `5.291667~5.458333`（4 帧）**只剪掉了 3 帧**，
   **最黑那一帧留在成片里**（观众看到的就是"画面无故一黑"），而音轨却按整段秒值多切了一帧 ⇒ 音画错位。
   根因是判据拿**日志里 `%.6f` 打印的秒**当窗口，而真实 pts 是 `127/24＝5.2916666…`（比打印值**小**）。
   本轮修掉（帧号窗口 + 存量修复入口），门 6 条、反向验证 6/6。

### 2.2 shot_1 那一处 47 的跳变：**是死黑帧**（VLM 原话）

抽 f115 / f127 / f140 交平台自己的 VLM（`deepseek-flash`）读图，原话（照抄，未改写）：

> 第127帧：纯黑帧，无任何可见画面内容。构图消失。
> 115→127：全黑，非自然光线变化，属于画面故障（黑帧）。
> 4) 一句话结论：包含死黑帧和面部畸形，该镜头画面不可用。

逐帧亮度佐证（同一镜）：`f126=63.3 → f127=16.1 → f128=17.1 → f129=19.3 → f130=21.7 → … 斜坡回到 f150=67`
⇒ **一帧骤降 + 约 1 秒斜坡回升**，是故障不是"灯灭了"。

### 2.4 那处黑帧在**成品片段**里还在（这就是本轮修的东西）

| 文件 | 帧数 | 时长 | `blackdetect`（平台同参 `d=0.02:pix_th=0.10:pic_th=0.98`） | 最暗帧 |
|---|---|---|---|---|
| ComfyUI 原档 `shot_1_00001_.mp4` | 192 | 8.000s | `black_start:5.291667 black_end:5.458333`（0.166667s ＝ **4 帧**） | 16.1@f127 |
| 平台成品 `clips/shot_001.mp4` | **189** | 7.875s | `black_start:5.291667 black_end:5.333333`（0.041667s ＝ **1 帧**） | 16.1@f127 |

⇒ 剪黑闪**跑了**（少 3 帧），但**最黑那一帧没被剪掉**；同一条命令手工复现：视频 189 帧/7.875s、**音频 7.84s**
（音频按整段 0.1667s 切 ⇒ **音轨比画面多切一帧**）。

**根因（逐帧 pts，实测）**：

```
f126 -> 5.250000   f127 -> 5.291667   f128 -> 5.333333   f129 -> 5.375000
f130 -> 5.416667   f131 -> 5.458333   （24fps，127/24 = 5.2916666…）
```

`blackdetect` 打印的是 `%.6f` 四舍五入值 `5.291667`，**比那一帧的真实 pts 大** ⇒ 用
`select='not(between(t,5.291667,5.458333))'` 去切，**f127 恰好落在窗口外**（f128/f129/f130 正常被切）。
对照实验：`between(n,127,130)`（按帧号）命中 4 帧，YAVG 依次 `16.0958 / 17.059 / 19.3264 / 21.7184`
—— 与 §2.2 的逐帧亮度逐字对上。

## 3. 本轮改了什么（代码）

### 3.1 `internal/compose/blackflash.go`：黑段 → **整数帧窗口**

* 新增 `frameSpan(r BlackRun, fps float64) (i0, i1 int, ok bool)`：`i0 = round(Start*fps)`、
  `i1 = round(End*fps) - 1`（`fps<=0` 用新常量 `defaultClipFPS = 24`）；短到落在同一帧内 ⇒ `ok=false`（丢帧丢不出它，不许虚报）。
* 剪辑表达式：视频 `between(n,i0,i1)`（`select` 的 `n` ＝ 输入帧序号，**实测确认**）、
  音频 `between(t,i0/fps,(i1+1)/fps)` ⇒ **画面与音轨丢的是同一批帧**，两边少掉的时长逐字相等。
* `removed` 改成按**帧数**算（`float64(cutFrames)/fps`），不再按日志里那个四舍五入过的秒值累加（那是虚报）。
* 新增 `ForceStripBlackFlash`：先删 `.noblack` 标记再走同一条链 —— **存量片段**带着"已处理过"标记，
  普通入口会直接 `return`（`cmd/clipfix` 的全部意义正是修存量，却会静默什么都不做）。
* `cmd/clipfix/main.go` 改走 `compose.ForceStripBlackFlash`（用法注释同步改成"已处理过的也重剪"）。

### 3.2 门（6 条，`internal/compose/blackflash_test.go`）

| 门 | 判据 |
|---|---|
| `TestFrameSpanSnapsRealBlackRunToWholeFrames` | **单位门**：真机秒值 `5.291667/5.458333` ⇒ 必须换成 `127..130`；偏大/偏小 1e-6 秒都不许漏帧；`fps=0` 用缺省 24 |
| `TestStripBlackFlashCutsRealMachineBlackRun` | **端到端（真机形态）**：灰 127 帧 → 黑 4 帧 → 灰 61 帧（192 帧/8.000s，黑段起点落在 127/24）+ 48k 音轨 ⇒ 剪完**一帧黑都不剩**、剪掉恰 4 帧、**画面与音轨都少 4 帧**（`audioDur` 用 ffprobe 单独量音轨） |
| `TestForceStripBlackFlashIgnoresMarker` | 标记有效时普通入口不动它，Force 入口照剪 |
| `TestClipFixBypassesProcessedMarkerInSource` | `cmd/clipfix` 必须走 Force（源码级机械守卫） |
| `TestParseBlackRunsRealLog` / `TestStrippableBlackRuns` | 既有（真机日志原文当夹具） |

**夹具为什么按帧数造**：旧门用 `color=…:d=1.0` 造黑段 —— 那时间戳是**二进制精确值**、窗口边界恰好落在帧上，
所以"最黑那一帧漏剪"**永远不现形**；真机是 `127/24` 这种循环小数才把它逼出来（同一条教训：假夹具掩盖缺陷）。

### 3.3 反向验证 6/6（`scratch/reverse_verify_blackflash.ps1`）

| # | 改坏 | 结果 |
|---|---|---|
| N1 | 视频改回按秒切 `between(t,r.Start,r.End)` | 端到端门**红** |
| N2 | `frameSpan` 起点取整去掉 `+0.5` | 单位门**红** |
| N3 | 音轨整段不切（窗口永不命中） | 端到端门**红** |
| N4 | `removed` 虚报帧数（语义型，不靠编译错） | 端到端门**红** |
| N5 | `clipfix` 改回普通入口 | 接线门**红** |
| N6 | `Force` 不删标记 | marker 门**红** |

**反向验证咬出我自己一条门太软**：N3 最初写的改法是"音频改回按黑段秒值切" —— **没变红**。复核后判定
那**不是缺陷**（打印值误差 ≤5e-7 秒，比一个音频采样还小），于是把 N3 换成"**音轨整段不切**"这个真缺陷，
并**补上 `audioDur`（量音轨时长）**：原来只量画面时长 ⇒ 音轨多切/不切它根本看不见。

## 6. 边界（如实）

* **本轮没有重渲任何一镜**（用户平台正在出片，GPU 在用）；上面所有"画面"结论都来自**已有真产物**的度量与 A/B，
  不是"接了补丁以后更好"的背书。
* **不接**任何第三方画面补丁 ⇒ 没有它们的实测数据（只有 README/源码原话与成本估算）。
* **存量片段不会自动重剪**：包括用户这一集已经渲完的 7 条（它们带着旧的 `.noblack` 标记，标记有效 ⇒ 后处理不再跑）。
  要修就 `go run ./cmd/clipfix -project "<项目 id>" -apply`（**现在会走 Force 入口**）。
  注意：改了片段内容会让清单里的指纹失配 ⇒ 平台会认为该镜"要重渲"（这是设计如此，不是 bug）。
* `deflicker` 只给了"两镜、同参、单次"的数据；**没有做多镜/多 seed 的稳定性验证**，也没看画面（只有数值 + SSIM）。
* latent 放大那条**没有跑过**，所以只写"待拍板 + 判据"，不写"更好"。
* `ffmpeg` 的 `deflicker` 会改动画面 ⇒ 任何"默认开启"的动议都必须先抽帧 A/B（本仓既有纪律）。
* 探针 `MANJUX_PROBE_CLIP` 只处理**副本**；本轮用它证明的是"那一帧死黑能被剪掉"，不是"整集观感变好了"。
