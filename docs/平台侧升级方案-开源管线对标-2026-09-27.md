## 2. 逐条方案

### P0-1 · 契约门的命中率统计（门的体检）

- **现状证据**：`internal/project/plan_contract.go:154 ValidatePlan()` 有 20+ 条判定（角色/场景/镜头 id、时长区间、说话人、景别白名单、画外音…），`Issue.Level` 只有 `fail`/`warn`。**没有任何地方统计"每条规则响过几次"。**
- **对标**：`shuohao-skills` 的 `.gates.jsonl` + stats —— 它明确把"**从没响过的门**"当作可疑项（可能是死门，或阈值过松）。
- **为什么这条排第一**：ManJuX 刚经历 61 条审计 → 49 条修复。修完没人知道**修的那条闸门是不是真的会响**。一条永远不响的 fail 门＝没有门。
- **动作**：给每条规则一个稳定 id（如 `plan.style.empty`、`shot.duration.out_of_range`），`ValidatePlan` 返回的 `Issue` 加 `RuleID` 字段；每次校验把 `{ruleID, level, 项目, 时间}` 追加到 `data/verify/gates.jsonl`；管理页加一个只读统计（各规则命中次数 + **零命中规则清单**）。
- **可机检判据**：跑一批真实项目后，**零命中的 fail 级规则必须逐条给出解释**（是确实没问题，还是阈值/判据写错了）。
- **工作量**：小（一个 `RuleID` 字段 + 一次 append + 一个只读页）。

### P0-2 · 参考图三档状态机（PLAN / REF / MISSING）

- **现状证据（2026-09-27 全量核过，与乙5 的记载已有出入）**：`RefPlan()` 返回 `(refs, roles, missing)`，**全库 5 个调用点里只剩 1 处静默丢弃**：

  | 调用点 | missing 去向 |
  |---|---|
  | `pipeline/refs.go:135`（`AssembleShotRefs` 内部） | 保留并返回给调用方 ✓ |
  | `pipeline/stages_render.go:224` | 接收，`len(missing)>0` 时告警（229-234 行）✓ |
  | `server/handlers_enhance.go:294` | 接收，走 `missingRefWarning()` 告警（298 行）✓ |
  | `server/handlers_enhance.go:515` | 同上（518 行）✓ |
  | **`pipeline/upgrade2k.go:101`** | **`refs, roles, _ = RefPlan(...)` ← 唯一剩余的静默点** ✗ |

  ⚠️ **乙5 记的 `handlers_enhance.go:159/336` 已过时** —— 那两处现在有专门的 `missingRefWarning()`，注释还留着这次修复的记录（"此前这里把 missing 直接丢进 _(静默降级)"）。
  **所以这条的性质变了：不是"机制缺失"，而是"最后一处漏网 + 缺状态化"。**
- **对标**：`drama-skills` 的三档参考态 —— `IMG-*` 只是提示词 / `PLAN-*` 是"作者将会提供"的参考 / `REF-*` 是**已存在于项目且校验过**的图；**只有 `REF-*` 允许绑进视频提示词的参考槽**。
- **动作**：
  1. 把 `missing` 的结果从"参数字符串"提升为**参考槽的状态**：每张卡三态 `planned` / `ready` / `verified`（verified = 已存在且过帧身份校验，与 4.1 的变体卡判据同源）；
  2. **渲染前断言**：进 `<Picture N>` 的必须是 `verified` 或至少 `ready`；`planned`/`missing` 一律**阻断或强提示**，且必须进界面与事件流；
  3. **补最后一处**：`upgrade2k.go:101` 改成接收并使用 missing —— 2K 升级路径现在与渲染期**共用 RefPlan 是为了防漂移**（见该文件 94 行注释），却把缺失丢掉了，等于 2K 产物可能建立在与渲染期不同的参考集上。
- **可机检判据**：任意一镜提交前，`roles` 里若含 `missing` → 该镜在界面上有明确标记；`AssembleShotRefs` 的测试补一条"missing 必须被上层消费"的断言。
- **工作量**：小-中（机制已有，主要是**不许丢** + 状态化 + 三处归一）。

### P0-3 · 锁面单一来源（LOCK-*）

- **现状证据**：同一角色的"不可变事实"目前分散在三处 —— `sysCastRules` 里 `image_prompt` 的身份前置结构（`director.go:174`）、`sysHard` 里 `retention_analysis` 的 `fully_preserved` 语义（`director.go:103`）、`animeFaceLock` 的画风锁（`director.go:210`）。三者措辞各自演化。
- **后果（已有实证）**：平台侧整改清单 §5.1 记的"**同一段里两套比例＝模型取中值**" —— 技能侧的比例句与平台的 `styleExpand` 介质块带不同比例词，模型折中，于是"定妆太丑"。
- **对标**：`drama-skills` 的 **continuity lock** —— 锁面写成**最短名词短语**，唯一目的就是"**能原样贴进提示词**"；一段锁面在多处被逐字复制，而不是各处重写。
- **动作**：
  1. 定义 `LOCK-<角色>-<属性>`（如 `LOCK-SHENYAN-FACE`、`LOCK-JIANGCHEN-DRESS`），锁面存**一句最短英文名词短语**（例：`olive-green stand-collar service dress`）；
  2. 定妆照 / 分镜 anchor / 视频提示词三处**逐字引用同一串**，任何一处不得改词、不得加近义词；
  3. 介质块（`artstyle.go`）与画风锁只允许写**画风层**的词，**不许写比例与五官**（比例归技能侧锚表 / 锁面）。
- **可机检判据**：同一 `LOCK-*` 出现在不同提示词里时，**字符串完全相等**（断言）；介质块里出现比例词即 fail。
- **工作量**：中（要梳理三处现有措辞并归一，但逻辑改动小）。

### P1-4 · 两段式直出 + 人工确认点

- **现状证据**：`SystemPrompt`（`director.go:219`）把 `characters` / `scenes` / `shots` 放在**一次**直出里（schema 见 `sysOutputFull`）—— 角色卡写错，该集所有镜头的参考图与提示词一起错。
- **对标**：`ai-comic-studio` 的四阶段各自带 **🛑 人工确认点**（Stage 1 剧本 / Stage 2 资产 / Stage 3 分镜），总分 ≥80 自动过、65–79 人工快审、<65 必须改；`shuohao-skills` 的纪律则是"**本阶段不许做下游的决定**"。
- **动作**（做成**可选**，不破坏现在的单轮路径）：
  - 增加"分段直出"开关：**第一段只出 `style` + `characters` + `scenes`**，界面确认（或一键重出）后再**第二段出 `shots`**；
  - 第二段的 system prompt 里，角色/场景**作为已冻结事实注入**并要求逐字引用锁面。
- **为什么值**：现在的失败代价是"一集全废"，分段后是"改一张卡"。
- **可机检判据**：第二段产出的 `characters` 必须与第一段**逐字一致**（若模型改动→fail，防止"确认后又漂"）。
- **工作量**：中（多一次 LLM 调用 + 一个确认 UI + 一致性断言）。

### P1-5 · 上游锁定（locked）

- **现状证据**：平台有资产复用与跨集复用（`asset_reuse_test.go`），但**没有"下游已启动 ⇒ 上游不可改"的语义** —— 改了定妆照，已铺开的分镜提示词不会自动知道。
- **对标**：`ai-comic-studio` 的 `status: locked` —— "下游启动后上游数据不可修改，防止不一致"。
- **动作**：Plan 的角色/场景卡加 `status`；某集进入渲染后卡转 `locked`；要改需**显式解锁**，并触发"受影响镜头"清单（哪些镜的 h3_prompt 引用了这张卡）。
- **可机检判据**：锁定态下修改上游 → 必须给出受影响镜头数，且这些镜标记为"需重出"。
- **工作量**：中。

### P1-6 · 每镜"视觉依据"清单

- **现状证据**：`PICTURE MANIFEST` 由**渲染期**追加（`stages_render.go:261` 的 `EnsureRefManifest`；另有 `upgrade2k.go:104` / `handlers_enhance.go:303` / `:522` 三个调用点），LLM 侧被明确要求"**不要猜图片总数**"（`director.go:90`）。但 Plan 里**没有一份"本镜用到了哪些资产"的显式清单**可供机检。
  - 值得注意的**正面设计**：`refmanifest.go:37` 记着有一道闸门 `TestRefPlanAndManifestArePairedAtEveryCallSite` —— **"每个调用点都配对 RefPlan + EnsureRefManifest"是被测试盯住的**。P1-6 要加的东西应当沿用这个模式（加断言，而不是加约定）。
- **对标**：`drama-skills` 的 **冻结关键帧 + 视觉依据** —— 每镜写死起点图，再回填"这一帧里谁/哪/什么必须保持一致"，**凡是关键帧里点名的，必须在依据清单里出现**；`oh-story-dsh` 把它做成了带行号的报错（`SHOT-EP001-002 的来源 EP001-SC009 在剧本中不存在。分镜.md:21`）。
- **动作**：Plan 的 `shots[]` 增加 `evidence`（资产 id 列表）；渲染前校验"`h3_prompt` / `characters` / `scene` 里点名的主体 ⊆ `evidence`"，不符**列出镜号**（而不是默默补）。
- **可机检判据**：悬空引用 = 0；报错形态对齐 oh-story-dsh（镜号 + 出处）。
- **工作量**：小-中。

### P2-7 · 契约三级：blocker / major / minor

- **现状证据**：`Issue.Level` 只有 `"fail"`（拒收）/ `"warn"`（收但提示）。
- **对标**：`ai-comic-studio` 的 `blocker`（阻塞下一阶段）→ `major`（需人工确认）→ `minor`（自动记录）。
- **动作**：保留 `fail`/`warn` 语义不变（避免破坏既有闸门与测试），**新增 `major`**：介于两者之间 —— 收下但**必须人工点确认**；配套：哪些现有 `warn` 该升 `major`（例如"说话人不在角色表里"`plan_contract.go:304`——它现在只 warn，而实测后果是整场变旁白）。
- **工作量**：小。

### P2-8 · 集级时长对账（把常量连成链）

- **现状证据**：已有 `CharsPerSecond=4.5`、`MinShotSeconds`/`MaxShotSeconds`、`GenMinShotSeconds=5`、`NeededShotSeconds()`（`dialogue.go`）—— **单镜级是对的**。
- **缺口**：没有**集级**对账。`短剧剧本分镜量化口径` 的约束链是 `台词秒 ≤ 分镜秒 ≤ 5 秒 ≤ 段 15 秒 ≤ 集 ±15%`，**每级逐条对账，"任何一层改动不静默破坏另一层"**。
- **动作**：加一条集级校验 —— 该集 `Σ shots.duration` 与目标时长（`Options.TotalSeconds`）偏差超 ±15% 报警；再给"段"（同场景连续镜）加 15 秒上限提示。
- **可机检判据**：集时长偏差 >15% → 报出具体差值，不静默。
- **工作量**：小。

### P2-9 · 造型变体的"变化记录"

- **现状证据**：整改清单 §4.1 已定"变体卡从主卡图生图派生"、§4.2 已定"同角色多卡按名字前缀归一人"。**但没人回答"这一场为什么该换装"。**
- **对标**：`huohuo-drama` 的 **因果链模式** —— 每章结尾一个 Change Record，每个状态转移必须写明 **trigger → process → outcome**，系统跨章存储/注入/审核。
- **动作**：变体卡带上 `trigger`（例：`进入收容所 → 换囚服档`），直出时把 trigger 注入该场 prompt；跨集时按 trigger 而非按镜号选卡。
- **价值**：现在"换装"依赖 LLM 临场判断或人工指定；有了 trigger，它就是**可复现、可审、可改**的一条规则。
- **工作量**：小。
