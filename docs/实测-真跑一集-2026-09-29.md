## 二、跑的第一件事：那 90 个分集是坏的

`data/projects/名册之外，八万零一号/` 下有 90 个分集项目（拆集建好了、没有 `plan.json`）。
真跑之前先核对"集号 ↔ 章号"，结果是：

```
ep 1 → 章不存在（内容是这本书 README 的「目录结构」一节）
ep 2 → 章不存在（内容是《六张表》里的一句话）
ep 3..10 → 第 1..8 章      （卷一）
ep 11..18 → 第 49..56 章   （卷七）
ep 19..26 → 第 17..24 章   （卷三）
...
```

两个原因（都是"看着一切正常"的那种）：

1. **README / research 稿被当成正文册**：`README.md` 第 34 行
   「第 1 章内有当场兑现、章末有倒计时钩子（详见 `research/审校记录.md` §二）。」
   正好命中章头正则 ⇒ 88 章的书写出 **90** 集，第 01 集是书的自述文档。
2. **卷序被路径序打乱**：章节按卷分目录（`正文/卷X_卷名/…`），而卷名的字节序与卷序无关
   （卷八 < 卷二 < 卷十）。旧实现按**路径**排序拼书，拆集遂按乱序编号 ——
   集名一个个都对，整本书的**集序与故事顺序脱钩**（批量产线会照着这个顺序拍下去）。

改法：收口径收进唯一的 `collectManuscript`（详见提交信息与
`internal/server/manuscript_collect_test.go`）。重拆后：**88 集，集号=章号**。

## 四、库索引（性能审计 #1）：漏了最热的那一路

### 4.1 怎么测的

`internal/library/perf_index_bench_test.go`：用**真实卡片**（`data/assets_library` 里
真跑出来的 `asset.json` 逐字照抄，只把 name/id/dir 唯一化）铺到 600 条，
按资产阶段的真实调用序列量时间。老代码的数字来自 **git worktree**
（`0edf822^`，加索引之前那一版），同一份 benchmark 文件、同一台机器、同一个夹具。

### 4.2 结果

| 场景（库 600 条） | 加索引之前 | 现在 |
|---|---|---|
| 单次按**卡 ID** 查（资产阶段每张卡第一步） | **25.5 ms** | **0.19 ms** |
| 一集 15 张卡，按卡 ID 查 | 211 ms | **1 ms** |
| 一集 15 张卡，按 ID 读+写交替（真实资产阶段） | 173 ms | **13 ms** |
| 一集 15 张卡，按显示名查（同名目录直接命中） | 3 ms | 1 ms |

**为什么之前没效果**：审计 #1 那次把 `matchByNameLocked` / `findWith` / `List` 改走索引，
**唯独漏了 `matchByIDLocked`**（还有 `findInFamily`）—— 而 `FindForCard(kind, cardID, …)`
正是资产阶段每张卡的第一步。也就是说"最热的那一路"从来没进过索引。

**第二个坑**：写操作原来让**整张**索引作废。资产阶段是"查一张、写一张"交替的，
实测「整份失效」**648 ms/集**，比"从来不加索引、每次全扫"（195 ms/集）**更慢**。
现在改成 `reindexLocked`：写完照着刚落盘的那一份**只更新这一条**。

### 4.3 守住在哪

* `index_scan_guard_test.go`：`readDirFn` 计数 —— **读路径零次目录枚举**；
  写完之后再读既零扫盘、又必须读到新值（少了后一半就是永久脏数据）。
* 这一条是**先写坏再确认**的：把 `matchByIDLocked` 临时改回"读路径顺手枚举一次目录"，
  守卫立刻红（`读路径扫了 3 次目录`）；改回来即绿。

### 4.4 还没验的

* 库 600 条是本机**造**的规模（真实库现在只有 13 条，真跑一集只用到这么多）。
  造法是"真实卡片复制到 600 条"，不是伪造字段 —— 但"40 集之后到底会不会有别的瓶颈"
  只能等真的跑到那个产量。
* 更早那版审计给的"每集白烧 1.6~2.6 秒"是推算；本机实测同等形态是 **173~211 ms/集**。

## 五、列表摘要缓存（性能审计 #6）：键指着不存在的路径

### 5.1 现场证据（真机）

02:10:20 方案落盘（13 镜、112 KB），之后 `GET /api/projects` 一直回：

```
id: 名册之外，八万零一号·第01集·重新检测到生命反应
has_plan: False   shots_total: 0   characters: 0   scenes: 0
```

直到重启都是这个值。原因：`projectSummary` 里 stat 的是
`<项目目录>/plan.json` 与 `<项目目录>/manifest.json`，而盘上的真实位置是
`plan/plan.json` 与 `clips/manifest.json`（`Store.PlanPath` / `Store.ManifestPath`）——
两个 `os.Stat` 永远失败 ⇒ mtime 恒为零值 ⇒ **第一次解析出来的摘要被永久命中**。

### 5.2 实测数字（`perf_list_bench_test.go`，88 个项目 × 真实方案 110 KB）

| 每次拉列表（前端每 15 秒一次） | 耗时 | 分配 |
|---|---|---|
| 命中缓存（现在） | **18.8 ms** | **20.8 MB** |
| 每次重解析（改动前等价口径） | 186.8 ms | 416.0 MB |

即：**10× 时间、20× 分配**；按 15 秒一次算，改动前仅"停在首页"就产生
≈ **1.66 GB/分钟** 的 GC 垃圾。

### 5.3 守住在哪

`project_summary_cache_test.go`：方案落盘 → 摘要必须变；改成 4 镜 → 必须再变
（显式推 mtime，避免粗精度文件系统假绿）。这条守卫**先写成"路径改坏"跑过一遍**，
确认会红。

### 5.4 真机复核（修完重编译重启之后）

```
GET /api/projects  →  88 个项目
  第01集   has_plan: True   shots_total: 13   shots_done: 1   characters: 7   scenes: 2
  第02集   has_plan: False  shots_total: 0    （确实还没跑，不是缓存假值）
```

修之前这里恒为 `has_plan: False / shots_total: 0`（§5.1）。

## 六、流式请求体（性能审计 #7）：峰值降下来了，但云端那条路仍缺 key

### 6.1 怎么测的

`internal/engine/h3api/perf_body_bench_test.go`：**同一个进程、同一份载荷、同一时刻**
对照两条链 —— 老写法 `fileToVideoDataURI`（整读 50MB → base64 → 拼接 → marshal）
与新写法 `createStreaming`（占位串 + 边读边编码），都真的发给一个本地 HTTP 服务端
（服务端真读 body，并断言两条链送出的字节数一致）。

载荷是真东西：一份 **48.8 MB 的真实 mp4**（`ffmpeg` 出的 768×1344/24fps/180s + 音轨，
云端 regeneration 的上限就是 50MB）+ 3 张真实参考图。

### 6.2 结果

```
峰值 HeapAlloc  老写法 254.3 MB（起 0.6） → 新写法 39.8 MB（起 0.5）
峰值增量        老 +253.7 MB            vs  新 +39.3 MB      （6.5×）
B/op（总分配）  老 471.0 MB/op          vs  新 69.1 MB/op    （6.8×）
服务端各收下 74.5 MB —— 两条链逐字节一致
```

### 6.3 还没验的（需要你给东西）

* **真云端跑不了**：`data/settings.json` 里 `minimax.api_key` 是**空的**
  （`/api/status` → `minimax_ready:false`）。所以"真发一次 MiniMax-H3 再生成"
  这条路没跑过 —— 要跑就配一个 key（或告诉我，我不擅自把别处的 key 填进你的配置）。
* 上面量的是**内存**与**等价性**；云端返回的产物校验（时长/音轨/短边）不在本轮范围。

## 七、顺带记下的现象（本轮不改，等拍板）

真跑才看得见的几处，属于"口径"而不是"缺陷"，按约定不擅自改：

1. **方案 title 为空**：日志打的是 `✔ 方案就绪:《》7 角色 / 2 场景 / 13 镜`，
   `plan.json` 里 `title` 是空串（`style` 有 64 字）。五步专职会话下没人负责填标题。
2. **③角色多视图会话失败**：`方案二次解析仍失败: JSON 合法但既无 title 也无 shots`，
   该会话返回的是"只有 characters 的 JSON"。其余会话不受影响，但这一步等于没做成。
3. **锚表把 5 个本集不出场的角色也建了卡**：方案本来只有 2 个角色，
   平台按锚表补进 霜见/墨洄/邵舷/尉迟彻/断桅 并各出一张定妆照（日志如实播报）。
   本集 13 镜用不到他们 —— 是为系列一致性预先付费，还是只建本集用到的？**待你定**。
4. **锚表补进来的角色卡实体类型判成了「物」**：`霜见` 在原著六张表里是**第二主角**，
   但资产阶段按文本推断把它当器物出图（`✔ 已生成:角色「霜见」(物)`）。
   补进来的卡没有 `kind` 字段，推断只能靠描述。
5. **首页列表在方案落盘瞬间报了 404 噪音**：`⚠ 项目「…」的分镜方案读不出来
   （open …\plan\plan.json: The system cannot find the file specified.）` ——
   发生在方案写完之前的一次轮询，属"读得太早"，但报的是 error 级文案。
